> - Neo4j 图查询通过 Supabase Edge Functions 代理，前端调用 Edge Function URL

> - 缓存操作使用前端内存缓存 + Zustand persist，替代原 Redis

> - Agent 进度推送改用 Supabase Realtime 的 Broadcast channel，替代原 WebSocket

> **所属模块：** 核心 Agent 系统

> **最后更新：** 2026-04-21

## 1. 功能概述

本功能定义了 AI 辅助长篇小说创作平台的多 Agent 协作体系。系统由一组职责明确、可独立运行的 Agent 组成，通过 Orchestrator（编排器）进行统一调度与任务路由，实现从意图识别、内容生成、质量审查到风格优化的全流程自动化协作。

体系分为四层：

1. **核心 Agent 组（A-01 ~ A-04）：** 负责编排、写作、审查和风格管理，是系统运行的主链路。
2. **设定 Agent 组（A-05 ~ A-07）：** 负责世界观构建、角色管理和连续性维护，为写作提供设定基础。
3. **辅助 Agent 组（A-08 ~ A-09）：** 负责大纲规划和灵感激发，在写作前提供结构化输入。
4. **协调层组件（A-10 ~ A-14）：** 负责角色状态桥接、伏笔协调和节奏分析，为各 Agent 提供跨模块的上下文支撑。

此外，系统还定义了结构化通信协议（A-15）、写作协作流程（A-16）、角色协调机制（A-17）以及循环检测与中断（决策 #52）、子 Agent 上下文隔离（决策 #53）等关键能力。

## 4. 业务规则

### 4.1 Agent 调度规则

| 规则编号 | 规则描述 |
|---------|---------|
| BR-01 | Orchestrator 是唯一有权调度子 Agent 的组件，子 Agent 之间不得直接调用。 |
| BR-02 | 所有子 Agent 必须通过结构化通信协议（A-15）返回结果，非结构化输出将被拒绝。 |
| BR-03 | 子 Agent 的并行执行需要 Orchestrator 明确授权，默认为串行执行。 |
| BR-04 | 当任务可拆解为无依赖关系的子任务时，Orchestrator 应优先选择并行执行以提升效率。 |

### 4.2 写作流程规则

| 规则编号 | 规则描述 |
|---------|---------|
| BR-05 | 标准写作流程（A-16）中的步骤顺序为建议顺序，作者可手动调整或跳过非必需步骤。 |
| BR-06 | WriterAgent 的快速模式仅降低审查轮次，不跳过 ReviewerAgent 的核心检查项。 |
| BR-07 | ReviewerAgent 的审查结果必须包含明确的通过/不通过判定及具体修改建议。 |
| BR-08 | StyleAgent 的风格变体生成数量默认为 2，作者可调整（范围 1-5）。 |

### 4.3 循环检测规则

| 规则编号 | 规则描述 |
|---------|---------|
| BR-09 | 循环检测的判定标准：同一对 Agent 连续 N 轮（默认 N=3）的输出相似度超过阈值（默认 90%）则判定为循环。 |
| BR-10 | 循环中断后，Orchestrator 必须将冲突信息、历史输出和裁决选项提交给作者。 |
| BR-11 | 工具调用去重的判定标准：相同工具名称 + 相同参数（精确匹配）则命中缓存。 |
| BR-12 | 缓存结果的有效期为当前任务会话内，跨会话不保留。 |

### 4.4 上下文隔离规则

| 规则编号 | 规则描述 |
|---------|---------|
| BR-13 | 每个 Agent 实例拥有独立的 token 预算，预算由 ContextBudgetManager（C-02）分配。 |
| BR-14 | Agent 间的数据传递仅通过结构化 JSON 摘要，不得传递原始上下文。 |
| BR-15 | 任务感知注入的过滤规则：WriterAgent 注入写作相关上下文，ReviewerAgent 注入审查相关上下文，以此类推。 |

### 4.5 角色协调规则

| 规则编号 | 规则描述 |
|---------|---------|
| BR-16 | 三种角色协调方案（A/B/C）可在项目设置中切换，切换后立即生效。 |
| BR-17 | 方案 A（Orchestrator 中心调度）为默认方案，适用于大多数写作场景。 |
| BR-18 | 方案 B（事件驱动协作）适用于需要高度自治的场景，如多线叙事。 |
| BR-19 | 方案 C（混合模式）结合 A 和 B 的优势，由 Orchestrator 处理关键路径，其余采用事件驱动。 |

## 5. 验收标准（AC）

### AC-01: Orchestrator 意图识别与任务路由

**前置条件：** 系统已初始化，至少有一个项目存在。

| 步骤 | 操作 | 预期结果 |
|------|------|---------|
| 1 | 输入模糊指令"帮我写下一章" | Orchestrator 识别为写作任务，触发标准写作流程。 |
| 2 | 输入指令"检查第三章的连续性" | Orchestrator 识别为审查任务，仅触发 ReviewerAgent。 |
| 3 | 输入复杂指令"写一段主角在雨中反思过去的场景，注意与第五章的伏笔呼应" | Orchestrator 拆解为：加载角色 → 检查伏笔 → 生成内容 → 审查，并按序执行。 |

### AC-02: WriterAgent 分段生成

**前置条件：** 项目已有世界观设定和角色信息。

| 步骤 | 操作 | 预期结果 |
|------|------|---------|
| 1 | 触发标准模式写作 | WriterAgent 按大纲分段生成，每段生成后自动提交 ReviewerAgent 审查。 |
| 2 | 切换到快速模式 | WriterAgent 降低审查轮次（最多 1 轮），生成速度提升 50% 以上。 |
| 3 | 查看生成结果 | 各段落之间衔接自然，无明显的逻辑断裂。 |

### AC-03: ReviewerAgent 统一审查

**前置条件：** WriterAgent 已生成一段内容。

| 步骤 | 操作 | 预期结果 |
|------|------|---------|
| 1 | 触发 ReviewerAgent 审查 | 返回结构化审查报告，包含：逻辑一致性、情节连续性、角色行为一致性、文风合规性、节奏合理性五个维度的评分（0-100）和具体建议。 |
| 2 | 存在连续性问题 | 审查报告中明确指出连续性冲突，引用相关章节和段落。 |
| 3 | 审查通过 | 所有维度评分 >= 80，标记为"通过"，内容可进入下一阶段。 |

### AC-04: StyleAgent 风格对比

**前置条件：** WriterAgent 已生成内容。

| 步骤 | 操作 | 预期结果 |
|------|------|---------|
| 1 | 触发 StyleAgent | 自动分析当前文本风格，生成至少 2 种风格变体。 |
| 2 | 查看对比视图 | 展示原文与各变体的并排对比，高亮差异部分。 |
| 3 | 采纳某个变体 | 点击采纳后，内容替换为该变体，后续写作沿用该风格。 |

### AC-05: 循环检测与中断

**前置条件：** 两个 Agent 之间存在潜在循环场景。

| 步骤 | 操作 | 预期结果 |
|------|------|---------|
| 1 | 模拟 WriterAgent 和 ReviewerAgent 连续 3 轮输出相似度 > 90% | 系统自动中断，弹出裁决面板。 |
| 2 | 查看裁决面板 | 展示冲突信息、历史输出摘要和裁决选项（采纳任一方/手动修改/跳过）。 |
| 3 | 相同参数的工具调用第二次执行 | 直接返回缓存结果，不重复调用。 |

### AC-06: 子 Agent 上下文隔离

**前置条件：** 多个 Agent 同时运行。

| 步骤 | 操作 | 预期结果 |
|------|------|---------|
| 1 | 检查 WriterAgent 的上下文 | 仅包含写作相关上下文（大纲、角色、伏笔等），不包含审查规则。 |
| 2 | 检查 ReviewerAgent 的上下文 | 仅包含审查相关上下文（审查规则、历史审查结果等），不包含写作草稿。 |
| 3 | 检查 token 使用统计 | 各 Agent 的 token 消耗独立统计，互不影响。 |

### AC-07: 写作协作流程

**前置条件：** 项目已有完整设定。

| 步骤 | 操作 | 预期结果 |
|------|------|---------|
| 1 | 触发标准写作流程 | 按顺序执行：角色加载 → 伏笔检查 → 大纲检查 → 节奏画像 → WriterAgent → ReviewerAgent → RhythmDetector → StyleAgent → 整合。 |
| 2 | 跳过非必需步骤 | 作者可选择跳过节奏画像和 StyleAgent，流程正常完成。 |
| 3 | 查看最终整合结果 | 整合后的内容包含所有 Agent 的贡献，格式统一。 |

### AC-08: 角色协调方案切换

**前置条件：** 项目已创建。

| 步骤 | 操作 | 预期结果 |
|------|------|---------|
| 1 | 默认方案 A | Orchestrator 中心调度，所有任务通过 Orchestrator 分配。 |
| 2 | 切换到方案 B | 切换为事件驱动，Agent 之间通过事件总线通信。 |
| 3 | 切换到方案 C | 混合模式，关键路径由 Orchestrator 管理，其余事件驱动。 |

## 6. 非功能性需求

| 编号 | 类别 | 需求描述 | 指标 |
|------|------|---------|------|
| NF-01 | 性能 | Orchestrator 意图识别响应时间 | < 2 秒（不含 LLM 调用） |
| NF-02 | 性能 | 子 Agent 并行执行时，总耗时不超过最慢子任务的 1.2 倍 | 并行效率 > 80% |

| NF-06 | 可扩展性 | 新增 Agent 的接入时间 | < 1 天（遵循协议即可） |
| NF-07 | 可维护性 | Agent 配置与业务逻辑分离 | Agent 可通过配置文件启停和调参 |
| NF-08 | 安全性 | 子 Agent 上下文隔离 | Agent 间无法直接访问彼此的原始上下文 |
