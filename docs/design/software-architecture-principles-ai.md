  修正 1：原 #12 "响应式编程（Functional Reactive Programming, FRP）"
  ─────────────────────────────────────────────────────────────────
  问题：原始定义"把一切视为随时间变化的数据流，用声明式操作组合"描述的
        是 Reactive Programming，不是 FRP。
  事实：FRP 由 Conal Elliott 和 Paul Hudak 于 1997 年在论文
        《Functional Reactive Animation》中提出，核心要求是连续时间语义
        （continuous time semantics），包含 behaviors（随连续时间变化的值）
        和 events（离散时间点的事件）。
        ReactiveX 官方明确声明：RxJS 等"是函数式和响应式的，但不同于 FRP"。
        RxJS 只有离散事件流，没有连续时间语义，因此不是 FRP。
  处理：标题改为"响应式编程（Reactive Programming）"，定义修正，
        注明与 FRP 的区别。

  修正 2：原 #25 缺失
  ─────────────────────────────────────────────────────────────────
  问题：原列表从 #24（Security by Design）直接跳到 #26（ISO 25010），缺 #25。
  推断：Security by Design 在软件工程课程和行业标准中几乎总是与
        Privacy by Design 配对出现。Privacy by Design 由安大略省前隐私专员
        Ann Cavoukian 提出，包含 7 项基础原则，已被 GDPR 第 25 条编入法律。
  处理：补全为 #29 Privacy by Design，置于 Security by Design 之后。

  修正 3：原 #23 拆分
  ─────────────────────────────────────────────────────────────────
  问题：原 #23 将熔断器、重试+退避、限流、幂等性、最终一致性 5 个独立概念
        合并为 1 条，AI 无法判断在什么场景应用哪一条。
  处理：拆为 5 个独立条目（#23-#27），每条有独立的适用场景和执行规则。

================================================================================
  第一类：架构模式（系统级选型）
================================================================================

  【选型决策树】
  ─────────────────────────────────────────────────────────────────
  Q1: 系统需要与多种外部系统（数据库、消息队列、第三方 API）交互？
    ├─ 是 → Q2
    └─ 否 → 分层架构即可

  Q2: 领域逻辑复杂，需要保护核心业务不被外部技术变化影响？
    ├─ 是 → Q3
    └─ 否 → 分层架构 + 依赖注入

  Q3: 需要显式定义端口（接口契约）隔离所有外部交互？
    ├─ 是 → 六边形架构
    └─ 否 → Q4

  Q4: 需要更细粒度的层级划分（领域服务、应用服务等）？
    ├─ 是 → 洋葱架构
    └─ 否 → 六边形架构

  Q5: 读写负载差异极大，或读模型和写模型需要独立演化？
    ├─ 是 → CQRS（配合 DDD）
    └─ 否 → 不使用 CQRS

  Q6: 需要完整审计轨迹和任意时间点状态回溯？
    ├─ 是 → 事件溯源（常与 CQRS 搭配）
    └─ 否 → 不使用事件溯源

  Q7: 组件间需要完全解耦，生产者不关心谁消费？
    ├─ 是 → 事件驱动架构（EDA）
    └─ 否 → 直接调用

  Q8: 系统中存在大量独立并发实体，每个实体有私有状态？
    ├─ 是 → Actor 模型
    └─ 否 → 传统并发模型

  Q9: 团队规模 > 8 人且业务域可清晰切分？
    ├─ 是 → 微服务
    └─ 否 → 单体（模块化单体）

  注意：架构选型必须经用户确认。AI 不得自行切换架构风格。


────────────────────────────────────────────────────────────────
  1. 分层架构（Layered Architecture）
────────────────────────────────────────────────────────────────

  定义：按职责垂直切分代码，每层只与相邻层通信，依赖方向单向向下。
  典型分层：表示层 → 应用层 → 领域层 → 基础设施层。

  适用场景：
    - 中小型项目，业务逻辑不过于复杂
    - 团队对其他架构模式不熟悉
    - 传统的 Web 应用（Controller → Service → Repository → DB）

  不适用场景：
    - 系统需要同时支持多种前端（Web、Mobile、CLI）→ 考虑六边形架构
    - 领域逻辑是系统核心价值，需要严格隔离 → 考虑洋葱架构
    - 读写模型需要独立扩展 → 考虑 CQRS

  AI 执行规则：
    1. 每层只能调用直接下层，禁止跨层调用（如 Controller 直接调 Repository）。
    2. 依赖方向必须单向向下，下层不得引用上层。
    3. 表示层不得包含业务逻辑，只负责输入验证和输出格式化。
    4. 基础设施层不得包含业务规则，只负责技术细节（DB、消息队列、外部 API）。
    5. 层间通信通过接口（抽象），不通过具体实现。

  概念关系：
    - 六边形架构和洋葱架构是分层架构的演进，解决了分层架构中
      "基础设施层在底部，领域层依赖它"的依赖方向问题。
    - 分层架构是所有其他架构模式的基础认知模型。


────────────────────────────────────────────────────────────────
  2. 六边形架构 / 端口适配器（Hexagonal / Ports & Adapters）
────────────────────────────────────────────────────────────────

  定义：由 Alistair Cockburn 于 2005 年提出（Cockburn 本人更倾向称之为
  "Ports and Adapters"）。把应用核心（业务逻辑）放在中心，通过端口（接口）
  与外部通信，外部通过适配器实现端口。核心不关心外部技术细节。

  适用场景：
    - 系统需要与多种外部系统交互（多种数据库、消息队列、第三方 API）
    - 需要对核心逻辑进行完全隔离的单元测试（不依赖任何基础设施）
    - 外部技术可能变化（如从 MySQL 迁移到 PostgreSQL）

  不适用场景：
    - 简单 CRUD 应用，无复杂业务逻辑 → 分层架构即可
    - 项目规模极小，定义端口的成本超过收益

  AI 执行规则：
    1. 应用核心定义端口接口（Port），适配器实现端口。
    2. 依赖方向：适配器依赖端口，端口依赖核心，核心不依赖任何外部。
    3. 每个外部交互（DB、消息队列、HTTP API、CLI）必须有对应的端口接口。
    4. 端口接口定义在核心层，适配器实现在外层。
    5. 测试时用 Mock 适配器替换真实适配器，核心逻辑完全不依赖基础设施。
    6. 禁止在核心代码中出现 import 数据库驱动、HTTP 框架等基础设施代码。

  概念关系：
    - 与洋葱架构同属一个架构家族，核心思想相同（依赖向内）。
    - 六边形强调"端口"的显式定义；洋葱强调"层级"的划分。
    - Cockburn 2023 年更新的文档明确指出：洋葱架构和 Clean Architecture
      与六边形具有相同的依赖结构，区别在于洋葱要求额外层级、不要求端口规范。
    - 两者可同时使用：用六边形的端口思想定义接口，用洋葱的层级组织代码。


────────────────────────────────────────────────────────────────
  3. 洋葱架构（Onion Architecture）
────────────────────────────────────────────────────────────────

  定义：由 Jeffrey Palermo 于 2008 年提出。同心圆结构，依赖方向永远向内，
  最内层是 Domain Model。外层可以依赖内层，内层不得依赖外层。
  典型层级（从内到外）：Domain Model → Domain Service → Application Service →
  Infrastructure。

  适用场景：
    - 领域模型是系统核心，需要最严格的保护
    - 需要明确的层级划分（不仅仅是"核心 vs 外围"）
    - 团队采用 DDD 方法论

  不适用场景：
    - 简单 CRUD 应用 → 分层架构
    - 不需要区分领域服务和应用服务 → 六边形架构

  AI 执行规则：
    1. Domain Model 层（最内层）不得依赖任何外层，不得引用任何框架。
    2. Domain Service 层依赖 Domain Model，不得依赖 Application Service 或 Infrastructure。
    3. Application Service 层依赖 Domain Service 和 Domain Model，编排业务用例。
    4. Infrastructure 层（最外层）依赖所有内层，实现技术细节。
    5. 依赖方向永远向内，违反此规则等于架构缺陷。
    6. 内层通过接口定义需要的能力（如 Repository 接口），外层实现。

  概念关系：
    - 与六边形架构同源，Cockburn 本人确认两者依赖结构相同。
    - 洋葱增加了层级划分（领域服务 vs 应用服务），六边形不要求额外层级。
    - 与 Clean Architecture（Robert C. Martin）高度相似，可视为同义。
    - 与 DDD 天然搭配：Domain Model 层对应 DDD 的实体和值对象。


────────────────────────────────────────────────────────────────
  4. 领域驱动设计（Domain-Driven Design, DDD）
────────────────────────────────────────────────────────────────

  定义：由 Eric Evans 提出。以领域模型为核心，让代码反映业务语言。
  核心概念：通用语言（Ubiquitous Language）、限界上下文（Bounded Context）、
  实体（Entity）、值对象（Value Object）、聚合（Aggregate）、
  聚合根（Aggregate Root）、领域事件（Domain Event）、仓储（Repository）。

  适用场景：
    - 业务领域复杂，规则多且易变
    - 业务专家和开发团队需要共同理解业务
    - 系统的核心价值在于业务逻辑而非技术实现

  不适用场景：
    - 简单 CRUD 应用，业务逻辑少 → 过度设计
    - 技术驱动型系统（如基础设施、中间件）→ DDD 价值不大

  AI 执行规则：
    1. 代码中的命名必须与业务专家使用的术语一致（通用语言）。
    2. 每个限界上下文必须有明确的边界，上下文间通过接口或事件通信。
    3. 聚合根是外部访问聚合的唯一入口，禁止绕过聚合根直接操作内部实体。
    4. 聚合内的一致性是强一致的，聚合间是最终一致的。
    5. 值对象必须不可变（immutable），两值对象相等当且仅当所有属性相等。
    6. 实体有唯一标识，两个属性完全相同但 ID 不同的实体是不同实体。
    7. 领域事件命名使用过去式（OrderPlaced, PaymentCompleted）。
    8. 一个聚合内禁止引用另一个聚合的实体引用，只通过 ID 引用。

  概念关系：
    - DDD 与洋葱架构天然搭配：Domain Model 层放 DDD 实体和值对象。
    - DDD 的 Repository 模式与六边形架构的端口思想一致。
    - DDD 的限界上下文常对应微服务的服务边界。
    - CQRS 常在 DDD 的应用层实现，分离命令（写）和查询（读）。


────────────────────────────────────────────────────────────────
  5. 微服务 vs 单体（Microservices vs Monolith）
────────────────────────────────────────────────────────────────

  定义：
    单体：所有模块在一个进程内，共享数据库，统一部署。
    微服务：按业务域拆成独立部署的服务，每个服务有自己的数据存储，
    服务间通过网络通信。

  适用场景（微服务）：
    - 团队规模 > 8 人，可按服务拆分团队
    - 业务域可清晰切分为独立边界
    - 不同模块的扩展需求差异大（如订单服务需高可用，报表服务需大数据量）
    - 需要独立部署和故障隔离

  适用场景（单体）：
    - 团队规模小（< 8 人）
    - 业务域尚未清晰，边界可能变化
    - 系统复杂度尚不需要分布式
    - 首期 MVP 快速验证

  AI 执行规则：
    1. 默认使用模块化单体（Modular Monolith）：单体部署但模块间通过
       接口通信，不直接引用内部实现。为未来拆分微服务做准备。
    2. 切分微服务的边界必须基于业务域（DDD 限界上下文），禁止按技术层切分。
    3. 每个微服务必须有独立的数据存储，禁止多个服务共享数据库。
    4. 服务间通信优先使用异步事件，同步调用仅用于必须即时响应的场景。
    5. 服务间通信必须设置超时和熔断器，禁止无限等待。
    6. 禁止在单体中引入微服务的分布式复杂性（如服务发现、API 网关），
       除非确实拆分为微服务。

  概念关系：
    - 微服务边界通常对应 DDD 的限界上下文。
    - 微服务间通信常采用事件驱动架构（EDA）。
    - 微服务中常使用熔断器、重试、限流等弹性模式（第五类）。


────────────────────────────────────────────────────────────────
  6. 事件驱动架构（Event-Driven Architecture, EDA）
────────────────────────────────────────────────────────────────

  定义：组件通过生产/消费事件通信，彼此不知道对方存在。
  生产者发布事件，消费者订阅事件，中间通过事件总线（Event Bus）或
  消息代理（Message Broker）路由。

  适用场景：
    - 组件间需要完全解耦
    - 一个操作需要触发多个不相关后续操作
    - 系统需要异步处理，不要求即时响应
    - 需要审计轨迹（事件天然是审计日志）

  不适用场景：
    - 需要即时同步响应 → 直接调用
    - 事件链路复杂且难以追踪 → 调试和排障困难
    - 系统简单，引入事件总线增加复杂度不划算

  AI 执行规则：
    1. 事件命名使用过去式（OrderCreated, PaymentFailed），表示已发生的事实。
    2. 事件必须是不可变的，发布后不可修改。
    3. 事件必须包含足够的上下文信息，消费者不应需要回查生产者。
    4. 事件处理失败必须有重试和死信队列（Dead Letter Queue）机制。
    5. 事件消费者必须幂等（见 #26 幂等性），同一事件被消费多次结果一致。
    6. 禁止事件链路超过 3 层（A→B→C→D），超过则重构为编排（Orchestration）。
    7. 必须实现事件溯源日志，记录事件发布顺序，便于排障。

  概念关系：
    - EDA 是事件溯源的基础设施。
    - EDA 常与 CQRS 搭配：写操作产生事件，读模型通过消费事件更新。
    - EDA 的消费者必须处理最终一致性（见 #27）。
    - EDA 在微服务架构中常作为服务间异步通信机制。


────────────────────────────────────────────────────────────────
  7. CQRS（Command Query Responsibility Segregation）
────────────────────────────────────────────────────────────────

  定义：由 Greg Young 提出。读和写用不同的模型，分离优化方向。
  命令（Command）负责写操作，不返回数据（只返回状态/ID）；
  查询（Query）负责读操作，不修改状态。

  适用场景：
    - 读写负载差异极大（写少读多，或写复杂读简单）
    - 读模型和写模型需要独立演化（如写用关系型 DB，读用搜索引擎）
    - 写操作有复杂业务规则，读操作只需简单投影

  不适用场景：
    - 读写模型差异不大，简单 CRUD 即可
    - 系统规模小，维护两套模型的成本超过收益
    - 需要强一致读写（CQRS 通常引入最终一致性）

  AI 执行规则：
    1. 命令和查询必须分离到不同的类/服务中，禁止混在一个 Service 里。
    2. 命令方法不返回业务数据，只返回操作结果（成功/失败 + ID）。
    3. 查询方法不修改状态，不调用写操作的 Repository。
    4. 命令和查询可以使用不同的数据模型和数据库。
    5. 如果使用事件溯源，查询模型通过消费领域事件构建物化视图（Read Model）。
    6. 命令必须包含意图（如 CancelOrder 而非 UpdateOrderStatus）。

  概念关系：
    - CQRS 与事件溯源独立但常组合使用（Microsoft 官方确认）。
    - 组合场景：需要审计轨迹 + 读写分离。
    - 不组合场景：简单领域，传统 CRUD 即可，不需要审计。
    - 渐进路径：先从事件溯源开始，仅当读模型优化需要时再加入 CQRS。
    - CQRS 常在 DDD 的应用层实现。
    - CQRS + EDA：命令产生事件，查询模型通过消费事件更新。


────────────────────────────────────────────────────────────────
  8. 事件溯源（Event Sourcing）
────────────────────────────────────────────────────────────────

  定义：不存当前状态，只存事件。状态由事件重放得出。
  每次状态变更存储为一个不可变事件，当前状态 = 所有事件按序重放的结果。

  适用场景：
    - 需要完整审计轨迹和状态变更历史
    - 需要时间查询（回溯任意时间点的状态）
    - 需要捕获业务意图（为什么变更，而非只是变为什么）
    - 并发更新冲突需要最小化（追加写入无锁冲突）

  不适用场景：
    - 简单或小型领域，传统 CRUD 即可
    - 需要实时一致性和即时视图更新（物化视图存在延迟）
    - 不需要审计轨迹和历史回放
    - 性能关键的写入场景（追加+事件发布有开销）
    - 团队无法承担额外复杂性（事件存储、投影引擎、读模型数据库、消息 broker）

  AI 执行规则：
    1. 事件存储（Event Store）只追加，不修改、不删除。
    2. 每个事件必须有唯一 ID、时间戳、类型、聚合 ID、版本号。
    3. 状态重建通过从事件存储读取该聚合的所有事件并按序重放。
    4. 事件版本必须有升级机制（upcast），处理旧版本事件的模式变更。
    5. 定期创建快照（Snapshot），避免重放大量事件。
    6. 禁止直接查询事件存储构建报表 → 使用物化视图（Read Model）。

  概念关系：
    - 与 CQRS 独立但常组合（见 #7）。
    - 事件溯源是事件驱动架构（EDA）的自然延伸。
    - 事件溯源要求最终一致性（见 #27）。
    - 事件溯源与 DDD 天然搭配：领域事件是事件存储的内容。


────────────────────────────────────────────────────────────────
  9. Actor 模型（Actor Model）
────────────────────────────────────────────────────────────────

  定义：一切皆 Actor。每个 Actor 有：私有状态（外部不可访问）、
  消息邮箱（接收异步消息）、行为（处理消息、发送消息、创建子 Actor）。
  Actor 之间只能通过异步消息通信，不共享内存。

  适用场景：
    - 系统中存在大量独立并发实体，每个实体有私有状态
    - 需要高并发但不想用锁和共享内存
    - 需要容错：Actor 崩溃后可由父 Actor 重启（监督策略）
    - 分布式系统，需要位置透明性（Actor 可在任意节点）

  不适用场景：
    - 简单并发，用 async/await 或 Promise 即可
    - 实体间需要共享大量数据（Actor 模型通过消息传递，不适合大数据量共享）
    - 团队不熟悉 Actor 模型，引入成本高

  AI 执行规则：
    1. Actor 状态不共享，外部只能通过发送消息与 Actor 交互。
    2. 消息处理是串行的：一个 Actor 同一时刻只处理一条消息。
    3. Actor 可以创建子 Actor，子 Actor 失败由父 Actor 决定处理策略
      （重启/恢复/停止/上报）。
    4. 消息必须不可变，禁止在消息中传递可变引用。
    5. Actor 间消息传递是异步的，不能假设消息到达顺序（除非使用持久化邮箱）。
    6. 禁止在 Actor 中执行阻塞操作（如同步 IO），会阻塞消息处理。

  概念关系：
    - Actor 模型是事件驱动架构的一种实现形式。
    - Actor 模型天然支持位置透明性，适合分布式系统。
    - Actor 模型与状态机（见 #15）结合：Actor 的行为可作为状态机。


================================================================================
  第二类：设计原则（代码级约束）
================================================================================

  【原则优先级】
  当原则冲突时，按以下优先级裁决：
    1. KISS > DRY > YAGNI（简单优先于去重，去重优先于不提前设计）
    2. SRP > OCP > LSP > ISP > DIP（单一职责是最基础的）
    3. 组合优于继承 > LSP（如果有继承，必须满足 LSP）
    4. 低耦合 > 高内聚（先解耦，再内聚）


────────────────────────────────────────────────────────────────
  10. SOLID 五原则
────────────────────────────────────────────────────────────────

  ── S — SRP（Single Responsibility Principle，单一职责）──

  定义：一个类/函数只有一个变化的理由。"变化的理由"= 谁会要求改它。
  如果有两个不同的角色（如财务和运维）会因不同原因要求修改同一个类，
  该类违反 SRP。

  AI 执行规则：
    1. 每个类/函数的职责用一句话描述，如果需要"并且"连接，则违反 SRP。
    2. 一个类只有一个变化轴线（axis of change）。
    3. 函数长度超过 40 行时检查是否违反 SRP。
    4. 一个类只有一个它服务的"角色"（stakeholder）。

  ── O — OCP（Open-Closed Principle，开闭原则）──

  定义：对扩展开放，对修改关闭。加新功能不改老代码，只加新代码。

  AI 执行规则：
    1. 新增功能通过新建类/函数实现，不修改已有类（除非修 Bug）。
    2. 使用策略模式、模板方法等模式实现 OCP。
    3. 当需要修改已有类才能加功能时，先提取接口，再新建实现。
    4. 禁止在 switch/case 或 if-else 中不断增加分支 → 用策略模式替换。

  ── L — LSP（Liskov Substitution Principle，里氏替换）──

  定义：子类必须能完全替换父类，程序行为不变。

  AI 执行规则：
    1. 子类不得比父类有更强的前置条件（不能拒绝父类接受的输入）。
    2. 子类不得比父类有更弱的后置条件（不能返回父类不会返回的值）。
    3. 子类不得抛出父类不会抛出的异常。
    4. 如果子类无法满足父类的所有行为契约，说明继承关系设计错误
       → 改用组合。
    5. 禁止子类方法抛出空实现或抛出 UnsupportedOperationException
       （说明不该继承）。

  ── I — ISP（Interface Segregation Principle，接口隔离）──

  定义：客户端不应依赖它不使用的方法。大接口拆成小接口。

  AI 执行规则：
    1. 接口的方法数不超过 7 个，超过则检查是否应拆分。
    2. 一个接口只服务一类客户端。
    3. 禁止让实现类实现它用不到的方法（空实现或抛异常）。
    4. 接口命名应反映使用方角色（如 ReadableRepository, WritableRepository
       而非一个大 Repository）。

  ── D — DIP（Dependency Inversion Principle，依赖倒置）──

  定义：高层模块不应依赖低层模块，二者都依赖抽象。
  抽象不应依赖细节，细节依赖抽象。

  AI 执行规则：
    1. 高层模块（业务逻辑）通过接口依赖低层模块（基础设施），不直接引用具体实现。
    2. 接口定义在高层模块中，实现在低层模块中。
    3. 依赖通过构造函数注入（见 #19 DI），不在函数内部 new 依赖。
    4. 禁止业务代码 import 基础设施框架（如直接 import 数据库驱动）。


────────────────────────────────────────────────────────────────
  11. DRY / KISS / YAGNI
────────────────────────────────────────────────────────────────

  ── DRY（Don't Repeat Yourself）──

  定义：知识/规则的单一来源。不是"代码看起来一样"。
  两段代码看起来一样但服务于不同业务规则，不违反 DRY。
  两段代码看起来不同但编码同一条业务规则，违反 DRY。

  AI 执行规则：
    1. 每一条业务规则、常量、配置只有一个定义来源。
    2. 禁止复制粘贴代码块超过 3 行 → 提取为函数。
    3. 如果两段代码"碰巧"相同但业务含义不同，不合并，标注注释说明。
    4. DRY 的粒度是"知识"而非"文本"，过度 DRY（错误抽象）比重复更糟糕。

  ── KISS（Keep It Simple, Stupid）──

  定义：简单优于复杂。不要用设计模式炫技。

  AI 执行规则：
    1. 能用 if/else 解决的不用策略模式。
    2. 能用函数解决的不用类。
    3. 能用简单数据结构解决的不用设计模式。
    4. 引入设计模式前必须说明"不引入会有什么问题"。
    5. 代码的复杂度应与问题的复杂度匹配，禁止过度设计。

  ── YAGNI（You Aren't Gonna Need It）──

  定义：不提前设计用不到的功能。

  AI 执行规则：
    1. 只实现当前需求明确要求的功能。
    2. 禁止"未来可能需要"为理由添加接口、抽象层或配置项。
    3. 禁止预留扩展点，除非需求文档明确要求。
    4. 如果当前不需要但未来可能需要，标注 TODO 并写明触发条件。


────────────────────────────────────────────────────────────────
  12. 低耦合高内聚
────────────────────────────────────────────────────────────────

  定义：
    低耦合：模块间依赖最少、接口最窄。
    高内聚：模块内所有元素共同完成一个明确职责，没有无关功能。

  判定标准（AI 必须用以下规则机械判定）：

  低耦合判定：
    1. 模块 A 修改内部实现，模块 B 不需要修改 → 耦合低。
    2. 模块 A 和模块 B 之间的接口方法数 ≤ 5 → 耦合低。
    3. 模块 A 不依赖模块 B 的内部数据结构 → 耦合低。
    4. 模块 A 可以独立测试，不需要 Mock 模块 B 的多个内部类 → 耦合低。
    5. 模块间通信通过接口，不通过具体类 → 耦合低。

  高内聚判定：
    1. 模块内所有方法都操作同一组数据 → 高内聚。
    2. 删除模块内任何一个方法会导致模块职责不完整 → 高内聚。
    3. 模块内方法间的调用是常态，模块外调用是例外 → 高内聚。
    4. 用一句话能描述模块的职责，不需要"并且" → 高内聚。
    5. 模块内没有"孤儿方法"（不被模块内任何其他方法调用，也不属于接口）→ 高内聚。

  AI 执行规则：
    1. 优先降低耦合，再提升内聚（低耦合是更重要的目标）。
    2. 模块间只通过接口通信，接口尽可能窄（方法少、参数少）。
    3. 禁止循环依赖：A 依赖 B，B 不得依赖 A → 提取共享接口或使用事件。
    4. 模块内不相关的功能必须拆分为独立模块。


────────────────────────────────────────────────────────────────
  13. 组合优于继承（Composition over Inheritance）
────────────────────────────────────────────────────────────────

  定义：优先使用组合（has-a）而非继承（is-a）复用代码。

  继承的问题：
    - 白盒复用：子类知道父类实现细节，破坏封装。
    - 强耦合：父类改一行，所有子类受影响。
    - 层级深：维护噩梦。
    - 静态：运行时无法切换父类。

  组合的优势：
    - 黑盒复用：只通过接口使用，不依赖实现细节。
    - 松耦合：改组件不影响使用方。
    - 扁平：无层级。
    - 动态：运行时可替换组件。

  AI 执行规则：
    1. 默认使用组合，只有"真正的 is-a 关系"才使用继承。
    2. 判定 is-a：B 是 A 的特化，B 可以在任何 A 出现的地方使用且行为正确
       （满足 LSP）。否则用组合。
    3. 继承层级不超过 2 层（祖父→父→子），超过必须重构为组合。
    4. 禁止用继承复用代码（"为了复用 A 的方法而继承 A"）→ 提取为独立组件，
       通过组合使用。
    5. 使用组合时，组件通过接口注入，不通过具体类注入。


────────────────────────────────────────────────────────────────
  14. 契约先行（Contract-First）
────────────────────────────────────────────────────────────────

  定义：先定义接口契约（schema/protocol），再写实现。
  契约是各方协作的唯一真相源（Single Source of Truth）。

  适用场景：
    - 多团队/多服务协作
    - 前后端分离，需要并行开发
    - API 需要稳定且向后兼容
    - 多语言系统集成

  AI 执行规则：
    1. 先定义接口 Schema（OpenAPI / gRPC proto / JSON Schema / GraphQL SDL），
       再写实现代码。
    2. Schema 文件是唯一真相源，代码从 Schema 生成，不从代码反向生成。
    3. Schema 变更必须遵循向后兼容规则：
       - 新增字段：可选，有默认值
       - 删除字段：先标记 deprecated，等所有消费方升级后再删除
       - 修改字段类型：禁止，新增新字段代替
    4. 消费方根据 Schema 生成客户端代码（code generation），不手写。
    5. 契约测试（Contract Testing）：提供方和消费方各自验证符合契约。

  第三类：编程范式

  【范式互斥/兼容关系】
  ┌─────────────────────┬──────────────────────────────────────────┐
  │ 范式                 │ 关系                                     │
  ├─────────────────────┼──────────────────────────────────────────┤
  │ 状态机 ↔ 响应式      │ 兼容：状态机可嵌入响应式流中             │

  │ 响应式 ↔ 单向数据流  │ 互斥：二选一，不混用                    │
  │ 单向数据流 ↔ 响应式  │ 互斥：二选一，不混用                    │
  │ 响应式 Store ↔ 单向  │ 互斥：Store 模式选一种                   │
  │                      │ 响应式 Store 是单向数据流的响应式变体    │
  └─────────────────────┴──────────────────────────────────────────┘

  AI 执行规则：
    1. 一个模块内只使用一种范式，不混用。
    2. 前端状态管理：单向数据流（Redux）或响应式 Store（MobX/Valtio）二选一。
    3. 后端异步流处理：响应式编程（RxJS/Observables）。
    4. 有明确状态机的业务逻辑：状态机模式。


────────────────────────────────────────────────────────────────
  15. 状态机（Finite State Machine, FSM）
────────────────────────────────────────────────────────────────

  定义：系统在任意时刻处于有限个状态之一，外部事件触发状态迁移。
  核心要素：状态（State）、事件（Event）、转移（Transition）、
  初始状态（Initial State）、终止状态（Terminal State）。

  适用场景：
    - 对象有明确的生命周期（订单：待支付→已支付→已发货→已完成/已取消）
    - 同一操作在不同状态下行为不同
    - 需要防止非法状态转移（如已取消的订单不能再发货）

  不适用场景：
    - 状态少于 3 个 → 用 if/else 即可
    - 状态转移规则简单且不会扩展 → 过度设计

  AI 执行规则：
    1. 所有可能的状态和转移必须显式定义在状态表中，禁止隐式状态。
    2. 非法状态转移必须抛出异常，不静默忽略。
    3. 每次状态转移可以触发副作用（如发事件、通知），但副作用不阻塞转移。
    4. 状态机实现使用状态模式或状态表（转移矩阵），不用 if/else 堆叠。
    5. 状态转移日志必须记录：前状态、事件、后状态、时间戳。
    6. 禁止"隐藏状态"（用布尔标志组合表示状态）→ 显式枚举所有状态。

  示例：
    // 状态定义
    type OrderState = 'pending' | 'paid' | 'shipped' | 'completed' | 'cancelled';
    type OrderEvent = 'pay' | 'ship' | 'complete' | 'cancel';

    // 转移表（不允许的转移不出现在表中 = 自动拒绝）
    const transitions: Record<OrderState, Partial<Record<OrderEvent, OrderState>>> = {
      pending:   { pay: 'paid', cancel: 'cancelled' },
      paid:      { ship: 'shipped', cancel: 'cancelled' },
      shipped:   { complete: 'completed' },
      completed: {},
      cancelled: {},
    };


────────────────────────────────────────────────────────────────
  16. 响应式编程（Reactive Programming）
────────────────────────────────────────────────────────────────

  定义：把一切视为随时间变化的数据流（Stream），用声明式操作组合。
  核心抽象：Observable（可观察数据流）、Observer（观察者）、
  Operator（流变换操作）、Subscription（订阅关系）。

  修正说明：
    原始文档将此条标记为"函数响应式编程（FRP）"，这是不准确的。
    FRP 由 Conal Elliott 于 1997 年提出，要求连续时间语义（continuous time），
    包含 behaviors（随连续时间变化的值）和 events（离散事件）。
    ReactiveX 官方明确声明：RxJS 等"是函数式和响应式的，但不同于 FRP"。
    本规范描述的是 Reactive Programming（如 RxJS、ReactiveX），
    不是 FRP。真正的 FRP 实现包括 Haskell 的 Yampa、Elm 的早期版本。

  适用场景：
    - 异步数据流处理（WebSocket、SSE、用户输入防抖）
    - 复杂的事件组合（多个异步源的协调、合并、过滤）
    - 需要背压（Backpressure）控制的数据流

  不适用场景：
    - 简单的 async/await 即可解决的异步 → 不需要 Observable
    - 简单的事件监听 → EventTarget.addEventListener 足够
    - 团队不熟悉响应式编程 → 调试难度高，误用易造成内存泄漏

  AI 执行规则：
    1. 所有 Observable 订阅必须在适当时机取消（unsubscribe），
       防止内存泄漏。使用 takeUntil、takeWhile 或 AsyncPipe 管理生命周期。
    2. 禁止在 Observable 内部产生副作用 → 使用纯函数操作符。
    3. hot Observable 和 cold Observable 必须显式区分，注明注释。
    4. 错误处理必须使用 catchError、retry 等操作符，禁止裸 subscribe。
    5. 禁止将 Observable 转换为 Promise 再用 async/await（除非在边界层）。
    6. 背压处理：生产者快于消费者时，必须使用 buffer、throttle、debounce
       或 switchMap 等策略。

  概念关系：
    - 响应式编程与单向数据流是互斥的状态管理范式（不混用）。
    - 响应式 Store（见 #18）是响应式编程在状态管理中的应用。
    - 响应式编程可与状态机结合：状态转移作为 Observable 流。


────────────────────────────────────────────────────────────────
  17. 单向数据流（Unidirectional Data Flow）
────────────────────────────────────────────────────────────────

  定义：数据沿单一方向流动：
    State → View → Action → Reducer → State
  典型实现：Redux、Vuex（严格模式）、NgRx。

  适用场景：
    - 前端应用状态复杂，需要可预测的状态变更
    - 需要时间旅行调试（Time-Travel Debugging）
    - 状态变更需要审计日志

  不适用场景：
    - 简单的组件内状态 → useState / useReducer 即可
    - 状态简单且无共享 → 局部状态足够

  AI 执行规则：
    1. 状态变更必须通过 Action → Reducer 路径，禁止直接修改 State。
    2. Reducer 必须是纯函数：相同输入相同输出，无副作用。
    3. Action 是普通对象，包含 type 和 payload，不可变。
    4. 副作用（API 调用、路由跳转）必须在 Reducer 之外处理
       （使用 Middleware / Epic / Saga）。
    5. State 树必须不可变（Immutable），更新返回新对象，不修改原对象。
    6. 全局 State 只有一个 Store，禁止多个全局 Store。

  概念关系：
    - 与响应式 Store 互斥（二选一）。
    - Reducer 本质是状态机的状态转移函数。
    - 单向数据流是 CQRS 在前端的体现：Action = Command，State = Read Model。


────────────────────────────────────────────────────────────────
  18. 响应式 Store（Reactive Store）
────────────────────────────────────────────────────────────────

  定义：状态是可观察的，依赖自动追踪、自动更新。
  典型实现：MobX、Valtio、Vue 3 Reactivity、SolidJS Store。
  与单向数据流的区别：不强制 Action → Reducer 路径，直接修改可观察状态，
  框架自动追踪依赖并触发更新。

  适用场景：
    - 状态结构复杂但更新模式简单（直接修改即可）
    - 需要细粒度的更新（只有依赖变化的组件重新渲染）
    - 不需要时间旅行调试

  不适用场景：
    - 需要严格的可预测性和审计日志 → 单向数据流
    - 需要时间旅行调试 → 单向数据流
    - 状态简单 → 局部状态足够

  AI 执行规则：
    1. 所有可观察状态必须用框架提供的 API 声明（如 MobX observable、Vue ref/reactive）。
    2. 修改状态必须在 Action / Transaction 中进行（MobX）或通过 API（Valtio），
       禁止在组件渲染函数中直接修改状态。
    3. 副作用使用 Reaction / Autorun / Effect 显式声明，不混在渲染逻辑中。
    4. 避免过度细粒度的可观察对象（每个字段都 observable），适当聚合。
    5. 状态变更必须是同步的（在 Action 内），异步操作完成后再修改状态。

  概念关系：
    - 与单向数据流互斥（二选一）。
    - 是响应式编程在状态管理领域的特化。
    - 响应式 Store 的依赖追踪机制使得细粒度更新更高效。


================================================================================
  第四类：模式与机制
================================================================================


────────────────────────────────────────────────────────────────
  19. 依赖注入（Dependency Injection, DI）
────────────────────────────────────────────────────────────────

  定义：对象不自己创建依赖，由外部容器注入。
  三种注入方式：构造函数注入（推荐）、属性注入（避免）、方法注入（少用）。

  AI 执行规则：
    1. 所有外部依赖通过构造函数参数注入，禁止在类内部 new 依赖。
    2. 依赖的类型必须是接口，不是具体类（DIP 原则）。
    3. 构造函数参数不超过 4 个，超过说明类职责过多 → 拆分。
    4. 禁止在构造函数中执行 IO 操作（如读配置、查数据库）。
    5. DI 容器的配置集中在组合根（Composition Root），不散落在业务代码中。
    6. 禁止 Service Locator 反模式（在类中调用容器获取依赖）→ 显式注入。


────────────────────────────────────────────────────────────────
  20. 仓储模式（Repository）
────────────────────────────────────────────────────────────────

  定义：为持久化提供集合式接口，屏蔽底层存储细节。
  业务代码通过 Repository 接口操作数据，不关心是 SQL、NoSQL 还是内存。

  AI 执行规则：
    1. Repository 接口定义在领域层，实现在基础设施层。
    2. Repository 方法名使用业务语言（findById, save, remove），
       不使用数据库语言（select, insert, delete, update）。
    3. Repository 返回领域对象（Entity / Aggregate），不返回 ORM 模型或 DTO。
    4. 一个聚合对应一个 Repository，不一个实体一个 Repository。
    5. Repository 不包含业务逻辑，只负责持久化。
    6. 禁止在 Repository 中暴露 IQueryable / 链式查询 → 查询方法参数明确。
    7. 分页查询必须返回总数和当前页数据，不返回裸 List。


────────────────────────────────────────────────────────────────
  21. 管道 / 中间件（Pipeline / Middleware）
────────────────────────────────────────────────────────────────

  定义：请求经过链式处理器，每层可前置/后置处理、可短路。
  典型场景：HTTP 请求处理（Express/Koa middleware）、数据变换管道、
  请求拦截器链。

  AI 执行规则：
    1. 每个中间件只做一件事（SRP）。
    2. 中间件必须能独立测试。
    3. 中间件顺序必须显式定义，不依赖隐式执行顺序。
    4. 中间件可以短路（不调用 next），短路时必须返回明确的响应。
    5. 中间件不能假设前一个中间件的存在（松耦合）。
    6. 错误处理中间件必须放在链的末尾，捕获所有未处理的错误。
    7. 中间件链深度不超过 10 层，超过说明职责划分有问题。


────────────────────────────────────────────────────────────────
  22. 装饰器 / AOP（面向切面编程）
────────────────────────────────────────────────────────────────

  定义：把横切关注点（日志、事务、权限、缓存）从业务代码剥离。
  通过装饰器/拦截器/代理在方法执行前后注入额外行为。

  AI 执行规则：
    1. 横切关注点（日志、事务、权限、缓存、指标）必须通过装饰器/拦截器实现，
       不侵入业务代码。
    2. 业务方法内不得包含与业务逻辑无关的横切代码（如手写日志、手动开事务）。
    3. 装饰器必须可独立测试。
    4. 装饰器执行顺序必须明确（如先权限检查、再日志、最后业务逻辑）。
    5. 装饰器不得修改业务方法的输入参数和返回值类型（透明性）。
    6. 一个方法上的装饰器不超过 3 个，超过说明方法职责不清晰。


================================================================================
  第五类：弹性与可靠性
================================================================================

  【弹性模式使用规则】
  所有外部调用（HTTP 请求、数据库、消息队列、第三方 API）必须同时具备：
    - 超时（Timeout）
    - 重试 + 指数退避（见 #24）
    - 熔断器（见 #23）
  缺少任一项等于缺陷代码。


────────────────────────────────────────────────────────────────
  23. 熔断器（Circuit Breaker）
────────────────────────────────────────────────────────────────

  定义：当下游服务连续失败达到阈值时，熔断器"打开"（Open），
  后续请求直接快速失败，不再调用下游。经过冷却时间后进入"半开"（Half-Open），
  放行少量请求探测恢复，成功则"关闭"（Closed），失败则重新"打开"。

  三种状态：
    Closed（关闭）→ 正常放行请求
    Open（打开）→ 直接快速失败，不调用下游
    Half-Open（半开）→ 放行少量探测请求

  AI 执行规则：
    1. 所有外部调用必须配置熔断器。
    2. 默认参数：失败率阈值 50%（最近 20 次请求中），冷却时间 30 秒，
       半开探测请求数 3 个。
    3. 熔断器打开时必须记录 WARN 日志，包含连续失败次数和最后错误信息。
    4. 熔断器状态变化（Closed→Open, Open→Half-Open, Half-Open→Closed）
       必须记录 INFO 日志。
    5. 熔断器打开时返回降级响应（Fallback），不返回 500 错误。
    6. 熔断器是实例级别的（每个下游服务一个熔断器实例），不是全局的。


────────────────────────────────────────────────────────────────
  24. 重试 + 指数退避（Retry + Exponential Backoff）
────────────────────────────────────────────────────────────────

  定义：调用失败时自动重试，每次重试间隔时间指数增长，
  并加入随机抖动（Jitter）避免重试风暴。

  AI 执行规则：
    1. 只有瞬态错误（网络超时、503、连接重置）才重试。
    2. 业务错误（400、401、403、404、422）不重试 → 立即失败。
    3. 默认参数：最大重试 3 次，初始间隔 1 秒，退避倍数 2，
       最大间隔 30 秒，抖动 ±20%。
       间隔公式：wait = min(initialDelay * 2^attempt, maxDelay) * jitter
    4. 重试次数耗尽后必须抛出异常或返回错误，不静默吞掉。
    5. 重试必须与熔断器配合：每次重试失败计入熔断器失败计数。
    6. 重试逻辑必须有总超时上限（如 60 秒），超过总超时则停止重试。
    7. 写操作重试必须确保幂等性（见 #26），否则重试可能导致重复操作。


────────────────────────────────────────────────────────────────
  25. 限流（Rate Limiting）
────────────────────────────────────────────────────────────────

  定义：限制单位时间内的请求数量，保护系统不被过载。

  常见算法：
    - 固定窗口（Fixed Window）：简单但有边界突刺问题。
    - 滑动窗口（Sliding Window）：更平滑，推荐使用。
    - 令牌桶（Token Bucket）：允许突发流量，适合 API 限流。
    - 漏桶（Leaky Bucket）：平滑输出，适合下游保护。

  AI 执行规则：
    1. 所有公开 API 必须配置限流。
    2. 默认参数：每用户每秒 10 请求，每分钟 100 请求，每小时 1000 请求。
    3. 限流策略使用滑动窗口或令牌桶，不使用固定窗口。
    4. 超过限流返回 429 Too Many Requests，响应头包含：
       X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset。
    5. 限流维度：按用户 ID > 按 IP > 按全局（优先级从高到低）。
    6. 内部服务间调用也需要限流，防止级联过载。


────────────────────────────────────────────────────────────────
  26. 幂等性（Idempotency）
────────────────────────────────────────────────────────────────

  定义：同一操作执行一次和执行多次，结果完全一致。

  AI 执行规则：
    1. 所有写操作（POST/PUT/DELETE）必须支持幂等性。
    2. 幂等键（Idempotency Key）方案：
       - 客户端生成唯一 ID，请求头携带 Idempotency-Key。
       - 服务端用此 Key 去重，相同 Key 的请求返回首次结果。
       - Key 的有效期至少 24 小时。
    3. PUT 操作天然幂等（用新状态完整替换旧状态）。
    4. POST 操作通过幂等键实现幂等。
    5. DELETE 操作幂等（删除已删除的资源返回 204，不报错）。
    6. 幂等检查必须在业务逻辑执行之前，避免重复执行副作用。
    7. 数据库操作使用乐观锁（版本号）或唯一约束实现幂等。


────────────────────────────────────────────────────────────────
  27. 最终一致性（Eventual Consistency）
────────────────────────────────────────────────────────────────

  定义：系统在停止接收新写入后，最终所有副本会收敛到一致状态。
  不保证任意时刻强一致，但保证最终一致。

  AI 执行规则：
    1. 聚合内一致性：强一致（同步操作，同一事务）。
    2. 聚合间一致性：最终一致（通过领域事件/消息异步同步）。
    3. 微服务间一致性：最终一致（禁止跨服务分布式事务，使用 Saga 模式）。
    4. 最终一致性的延迟必须可监控、可告警，延迟超过阈值必须告警。
    5. 必须实现对账机制（Reconciliation）：定期比对源数据和副本数据，
       发现不一致时修复。
    6. 向用户展示数据时，如果数据可能不一致，必须标注"数据可能延迟"。
    7. 禁止在最终一致性场景中使用先写后立即读（Read-Your-Writes）的假设。


================================================================================
  第六类：安全与质量
================================================================================


────────────────────────────────────────────────────────────────
  28. Security by Design
────────────────────────────────────────────────────────────────

  定义：安全不是事后附加，而是设计阶段就内建的核心属性。

  五项子原则：

  1. 最小权限（Least Privilege）
     只给完成任务所需的最小权限，不多给。
     AI 执行规则：
       - 服务账号权限按功能最小化分配。
       - API 端点权限按角色细分，不使用"管理员可访问所有"的粗粒度权限。
       - 数据库用户只授予所需表的 CRUD 权限，不授予 DDL 权限。

  2. 纵深防御（Defense in Depth）
     多层防护，一层被攻破不会导致全面沦陷。
     AI 执行规则：
       - 输入验证在前端、API 网关、业务层、数据库层各有校验。
       - 网络层（防火墙）、应用层（WAF）、代码层（参数化查询）多层防护。
       - 敏感操作需要多因素认证。

  3. 失败安全（Fail Secure）
     出错时进入安全态，拒绝访问而非放行。
     AI 执行规则：
       - 权限检查失败时返回 403，不返回 200 + 空数据。
       - 异常发生时默认拒绝操作，不默认放行。
       - Token 验证失败时清除会话，不降级为匿名访问。

  4. 经济性（Economy of Mechanism）
     安全机制成本要低于攻击成本。
     AI 执行规则：
       - 安全措施复杂度与资产价值匹配，不过度设计。
       - 验证码难度与业务风险匹配（登录用简单验证码，转账用人脸识别）。

  5. 零信任（Zero Trust）
     永不信任，始终验证。
     AI 执行规则：
       - 服务间通信必须认证和授权，不因"在内网"就跳过认证。
       - 每个请求必须验证 Token，不依赖 IP 白名单。
       - 数据库访问必须验证身份，不依赖网络隔离。


────────────────────────────────────────────────────────────────
  29. Privacy by Design（原缺失 #25 补全）
────────────────────────────────────────────────────────────────

  定义：由安大略省前隐私专员 Ann Cavoukian 提出。隐私保护不是事后补救，
  而是设计阶段就内建。已被 GDPR 第 25 条编入欧盟法律。

  与 Security by Design 的关系：
    Security by Design 保护系统完整性、可用性和机密性免受对抗性威胁（工程视角）。
    Privacy by Design 保护系统所处理的个人数据相关个人的权利（法律和伦理视角）。
    两者相关但独立，必须同时遵循。

  七项基础原则：

  1. 主动而非被动（Proactive not Reactive）
     在隐私事件发生前就预防，不是事后补救。
     AI 执行规则：设计阶段就识别个人数据流向，不等到上线后再补隐私措施。

  2. 隐私为默认设置（Privacy as the Default）
     用户无需采取任何行动就能享受隐私保护。
     AI 执行规则：
       - 默认关闭数据共享开关，用户主动选择才开启。
       - 默认使用最严格的隐私设置，用户可主动放宽。

  3. 将隐私嵌入设计（Privacy Embedded into Design）
     隐私保护是系统的核心组件，不是附加模块。
     AI 执行规则：隐私保护措施在架构设计中体现，不通过外挂插件实现。

  4. 端到端安全（Full Functionality — End-to-End Security）
     隐私保护不牺牲系统功能，两者同时实现。
     AI 执行规则：不通过"砍功能"来实现隐私，而是通过技术手段兼顾两者。

  5. 端到端保护（End-to-End Protection）
     数据从收集到销毁的全生命周期都有隐私保护。
     AI 执行规则：
       - 个人数据收集时明确告知用途。
       - 个人数据存储时加密。
       - 个人数据传输时 TLS 1.2+。
       - 个人数据销毁时彻底删除（包括备份）。

  6. 可见性与透明性（Visibility and Transparency）
     隐私实践可被独立验证。
     AI 执行规则：记录所有个人数据访问日志，可供审计。

  7. 尊重用户隐私（Respect for User Privacy）
     以用户利益为中心。
     AI 执行规则：
       - 提供数据导出功能（GDPR 数据可携带权）。
       - 提供数据删除功能（GDPR 被遗忘权）。
       - 提供数据修改功能（GDPR 更正权）。


────────────────────────────────────────────────────────────────
  30. 质量模型（ISO/IEC 25010）
────────────────────────────────────────────────────────────────

  定义：ISO/IEC 25010 定义了软件质量的八大特性。
  AI 在设计、编码、测试时必须对照以下特性自检。

  八大特性及 AI 执行规则：

  ┌──────────────┬──────────────────────────────────────────────────┐
  │ 特性          │ AI 执行规则                                       │
  ├──────────────┼──────────────────────────────────────────────────┤
  │ 1.功能适合性  │ - 每个需求有对应的测试用例                        │
  │ (Functional   │ - 边界值、异常路径、空输入都有测试                │
  │  Suitability) │ - 验收标准在编码前定义                            │
  ├──────────────┼──────────────────────────────────────────────────┤
  │ 2.性能效率    │ - 数据库查询使用索引，禁止 N+1 查询               │
  │ (Performance  │ - 列表查询必须分页                                │
  │  Efficiency)  │ - 大数据量使用流式处理                            │
  │              │ - 外部调用设置超时                                │
  │              │ - 响应时间 < 200ms（P95），< 1s（P99）           │
  ├──────────────┼──────────────────────────────────────────────────┤
  │ 3.兼容性      │ - API 遵循向后兼容规则（见 #14 契约先行）         │
  │ (Compatibility)│ - 浏览器兼容性：最新两个版本                      │
  │              │ - 数据格式遵循标准（JSON/JSON:API/REST）          │
  ├──────────────┼──────────────────────────────────────────────────┤
  │ 4.可用性      │ - 错误信息用户可理解，不含技术细节                │
  │ (Usability)   │ - 表单验证有即时反馈                              │
  │              │ - 加载状态有视觉指示                              │
  │              │ - 关键操作有确认提示                              │
  │              │ - 响应式布局适配移动端                            │
  ├──────────────┼──────────────────────────────────────────────────┤
  │ 5.可靠性      │ - 外部调用有熔断器和重试（见 #23, #24）           │
  │ (Reliability) │ - 关键数据有备份和恢复机制                        │
  │              │ - 系统故障后能自动恢复（健康检查 + 重启）         │
  │              │ - 事务保证原子性，失败时回滚                      │
  ├──────────────┼──────────────────────────────────────────────────┤
  │ 6.安全性      │ - 遵循 Security by Design（见 #28）              │
  │ (Security)    │ - 遵循 Privacy by Design（见 #29）               │
  │              │ - 所有输入经过白名单验证                          │
  │              │ - 敏感数据加密存储和传输                          │
  │              │ - 依赖库定期扫描漏洞                              │
  ├──────────────┼──────────────────────────────────────────────────┤
  │ 7.可维护性    │ - 遵循 SOLID 原则和命名规范                       │
  │ (Maintain-    │ - 函数 < 40 行，类 < 300 行                       │
  │  ability)     │ - 公共 API 有 TSDoc 文档                          │
  │              │ - 测试覆盖率 ≥85%（分支）/ ≥90%（语句）           │
  │              │ - 无循环依赖                                      │
  │              │ - 代码可静态分析通过（ESLint/TypeScript 严格模式）│
  ├──────────────┼──────────────────────────────────────────────────┤
  │ 8.可移植性    │ - 不硬编码文件路径、端口、主机名                  │
  │ (Portability) │ - 配置通过环境变量注入                            │
  │              │ - 不依赖特定 OS 特性                              │
  │              │ - Docker 容器化部署                               │
  │              │ - 数据库使用 ORM/抽象层，不直接写 SQL 方言        │
  └──────────────┴──────────────────────────────────────────────────┘


================================================================================
  附录 A：原则冲突裁决优先级
================================================================================

  当多条原则同时适用且产生冲突时，按以下优先级从高到低裁决：

  优先级 1（最高）：安全性 > 一切
    - 如果某做法提升安全性但违反其他原则，优先安全。
    - 例：参数化查询比字符串拼接慢（性能），但防 SQL 注入（安全）→ 安全优先。

  优先级 2：正确性 > 性能
    - 正确的结果比快速的结果重要。
    - 例：事务保证一致性但降低性能 → 一致性优先。

  优先级 3：KISS > DRY > YAGNI
    - 简单优先于去重，去重优先于不提前设计。
    - 例：两段代码相同但合并会引入复杂抽象 → 保持重复（KISS > DRY）。

  优先级 4：低耦合 > 高内聚
    - 先解耦，再内聚。
    - 例：将两个内聚但耦合高的模块拆开 → 解耦优先。

  优先级 5：组合 > 继承
    - 有疑问时用组合。
    - 除非满足严格的 is-a 关系（LSP 验证通过）。

  优先级 6：SRP > OCP > LSP > ISP > DIP
    - SOLID 内部冲突时，按此顺序裁决。

  注意：优先级 1 和 2 不可被覆盖。优先级 3-6 可以在代码注释中说明理由后
  覆盖，但必须标注 [DEVIATION: 原则X > 原则Y, 理由: ...]。

================================================================================
  附录 C：AI 架构决策检查清单
================================================================================

  AI 在做架构决策或编写代码前，必须逐项确认：

  【架构选型】
  □ 当前架构模式是否与项目现有架构一致？（不一致需用户确认）
  □ 是否引入了不必要的架构复杂度？（YAGNI 检查）
  □ 选型是否基于业务需求而非技术偏好？

  【代码结构】
  □ 依赖方向是否单向向内/向下？
  □ 是否有循环依赖？
  □ 每个类/函数是否只有一个职责？（SRP）
  □ 是否通过接口依赖而非具体类？（DIP）
  □ 是否使用组合而非继承？（除非满足 LSP）

  【外部交互】
  □ 所有外部调用是否有超时、重试、熔断器？
  □ 写操作是否幂等？
  □ 事件消费者是否幂等？
  □ 外部交互是否通过端口/接口隔离？

  【数据一致性】
  □ 聚合内是否强一致？
  □ 聚合间/服务间是否最终一致？
  □ 是否有对账机制？

  【安全与隐私】
  □ 是否遵循最小权限？
  □ 输入是否经过白名单验证？
  □ 敏感数据是否加密存储和传输？
  □ 是否默认保护用户隐私？（Privacy by Design）
  □ 失败时是否进入安全态？

  【质量】
  □ 代码是否通过类型检查（严格模式）？
  □ 测试覆盖率是否 > 80%？
  □ 公共 API 是否有文档？
  □ 错误信息是否用户友好？
