# 32 · 新功能三阶段流程规范（需求讨论 → 设计 → 实施）

- **状态**：用户拍板立项（2026-09-29）。**试验性流程**——从 resetAll（settings:resetAll，
  f99ae3a5→944b39fb）单样本归纳 + 既有项目纪律（定义表、写穿透、confirm store、棘轮门禁）
  形式化而来；每完成一个**不同形态**的新功能回审一次本文件并迭代（迭代规则见 §7）。
- **适用**：渲染层/主进程的功能级新增与修改。先过 §1 分级裁剪，trivial 修改不走全流程。
- **上游**：AGENTS.md「渲染层写法标准」「质量门禁顺序」「架构决策记录」；
  运行案例 = [31 号失效自动化](./31-invalidation-automation-spec.md) 与 resetAll 全过程。
- **配套教训来源**：技术债台账（棘轮连锁、注释漂移、台账腐烂、fail-silent）、E2E 测试手册。

## 0. 总纲：三阶段各回答一个问题

- 需求讨论回答「**问题是什么**」——用户可观察的痛点，禁止出现实现方案；
- 设计阶段回答「**方案是什么样**」——语义、结构、边界，仍是纸面；
- 实施阶段回答「**怎么落地且不烂尾**」——顺序、门禁、提交、收尾。

三个阶段最常见的失败模式各不相同：需求阶段**边界含糊**（实施到一半争论作用域）、
设计阶段**先画 UI 后想数据**（被实现逼进死角）、实施阶段**门禁连锁收尾才爆**
（棘轮三连拦在最后一刻）。

## 1. 功能分级裁剪（先定走哪条流程，防过重流程自我废弃）

三问判级：新增 IPC 方法？新增持久化/存储结构？含危险操作或跨进程副作用？

- **全量流程**（三问任一 yes）：完整走 §3 → §4 → §5，两个强制检查点（§2）不豁免；
- **轻量流程**（全 no 但有行为变化）：只写 §3.1-3.2（动机 + 语义边界）与验收标准，
  设计节并入需求文档，实施走 §5 的精简版（跳过棘轮预演的成文要求，门禁照跑）；
- **trivial**（纯文案/样式/注释/单行逻辑）：直接实施，i18n 双语与门禁照常。

（resetAll 例：新增 IPC + 危险操作 → 全量流程。）

## 2. 强制检查点（两个，缺一不进下一阶段）

- **CP1 边界拍板**（设计前）：需求节成文、语义边界与不做清单明确 → 用户（或评审）确认
  「边界无误、不做清单认可」才进设计。
- **CP2 设计评审**（实施前）：设计六方向逐节成文、每个有争议的语义选择均附依据与备选 →
  评审通过才动代码。评审形式：用户拍板，或 AI 交叉深读（参照三路深读模式，覆盖本文件
  §4 的必答问题清单）。

检查点不通过的处理：回上一阶段修订，**不携带分歧进入下一阶段**。

## 3. 需求讨论阶段（回答「问题是什么」）

产出 = 一句话问题陈述 + 边界清单。六个方向，禁止出现实现方案：

1. **问题与动机**：谁、在什么场景、遇到什么可观察的问题？不做的代价？
   （resetAll 例：调乱的设置没有一键归位，只能逐项手改或删数据文件。）
2. **语义边界（作用域契约）**：影响哪些数据/状态 + **显式不碰清单**。两者缺一不可。
   （resetAll 例：重置 app_settings 的 13 个 SETTING_KEYS；**不碰** API Key、会话历史、
   MCP/IM 渠道配置、OS 登录项。）
3. **验收标准**：做完后用户怎么验证对了？必须可观察，且直接作为 §4.7 测试设计的输入。
   （resetAll 例：预置非默认值 → 重置 → 回落出厂。）
4. **影响面盘点**：碰哪些进程/存储/既有契约？新增 IPC？schema 演进？直接决定风险等级。
5. **反例与边界场景点名**：并发/在途写入、断电、空态、无桥（浏览器模式）、平台差异。
   需求阶段只点名存在，不给解法。
6. **不做清单 + 待拍板项表**：显式写出「明确不做什么」防范围蔓延；有争议的取舍呈表格
   待拍板。（resetAll 例：不做自动备份——交互打断、导出按钮同区可见。）

## 4. 设计阶段（回答「方案是什么样」）

按依赖序六个方向 + 测试/安全/发布三个专项。每个方向落一节进设计文档；
**每个有争议的语义选择写「选了什么 / 依据 / 另一条为什么不选」**。

### 4.1 业务逻辑（最先，它决定一切）
- 纯函数核心是什么？能否抽 lib 层可测纯函数（check:functions/complexity 两道棘轮会审）；
- 语义选择附依据与备选（resetAll 例：删除键 vs 写默认值——选删除的三条依据：
  默认值真源唯一 / 表空即默认是不变式 / 更原子）；
- 失败路径三选一：fail-open / fail-closed / fail-silent（keychain getSecret 教训：
  fail-silent 被审计点名）；
- 复用清单先扫：现成 API 优先于新建（resetAll 复用 applySettingsSnapshot，零新增）；
- 安全边界：输入校验、错误码来源、凭据边界。

### 4.2 数据管理
- 真源在哪（SQLite / keychain / 内存）；**缺失语义**——键缺失时的行为必须逐一
  实证主进程消费方的兜底，不能假设（resetAll 例：readCloseAction / isAutoCheckEnabled /
  syncTitleBarOverlayFromTheme 三处兜底逐一核验）；
- 写入路径与事务边界（单键 / 批量事务）；**竞态防线**（在途写穿透未落库时 DELETE
  会旧值复活 → flushPendingSettings 先行）；
- schema 演进走 drizzle-kit generate，禁手写 SQL；
- 配套导出/导入/清理是否受影响。

### 4.3 契约/IPC（本项目第一公民，用户清单外必列）
- 定义表三步：meta + definitions + handler；响应 schema 必写（R3 契约校验）；
- **mock-api 同批对齐**——IpcApi 的实现者缺一个 typecheck 就挂（resetAll 实施中
  dev server FATAL「handler 缺失」实证：契约体系 fail-fast 反而是在帮忙）；
- 是否需要主进程主动广播（broadcastSettingChanged / 31 号失效域声明）。

### 4.4 状态管理（四层判定）
- 判定表：IPC invoke → L3 Query；事件推送 → L4 桥；跨组件共享 → L2 Zustand；
  组件独享 → L1 useState；
- 优先复用现成批量 API（applySettingsSnapshot / applyMainSettingChange），不造第二套；
- 乐观更新五要素（cancel / 快照 / 回滚 / onSettled / onSuccess 语义区分）；
- **file-size 棘轮预判**：目标文件接近 600 净行时，新逻辑放 lib/ops 层而非往 store 塞。

### 4.5 UX 设计
- 入口与信息架构：放哪个分区、与什么操作相邻（resetAll 与设置导出/导入同区——
  同属维护操作）；
- **危险等级与确认模式**：danger confirm 文案三要素——影响范围清单 + 明示不影响项 +
  不可撤销提示与备份引导；
- 反馈闭环：成功/失败 toast，错误经 unwrapErrorMessage 本地化；
- 空态/加载态/错误态；i18n 双语（确认框文案同样双语）。

### 4.6 UI 设计（最后）
- 组件库对齐（ui/button、Label、SectionTitle/SettingRow）；无裸色值（check:tokens 卡）；
- 既有分区布局形态；动效走 MotionVault 不手写。

### 4.7 测试与安全（**设计决策，不是实施细节**）
- 测什么、哪些是红灯夹具、行为断言怎么写（resetAll 例：「预置非默认值 → 重置 →
  回落出厂」这条断言在设计期就写进验收）；
- 存储层用真实 SQLite 临时库（无业务 mock）；组件测试断言 store 实质状态；
- 安全：危险操作确认、凭据不回传、白名单防御。

### 4.8 发布与复盘（2026-09-29 补丁⑤）
- 成功指标是什么？错误信号走哪条通道（OTEL 单通道 / 本地日志随诊断包）；
- 是否先进 experimental 分区观察采用率再转正；
- 复盘节奏与锚点（本地优先无遥测明细时，复盘锚 = 用户反馈 + 诊断包）。

### 4.9 多入口盘点（2026-09-29 补丁⑥）
- 本功能全部用户可达入口清单（主题四入口；托盘菜单也能改关窗行为——
  applyMainSettingChange 就为此存在），保证多入口同源，不出现双份状态。

## 5. 实施阶段（回答「怎么落地且不烂尾」）

1. **提交切分**：按逻辑（地基 → 契约 → handler → renderer → i18n → mock），
   每个提交独立可编译、可回退；
2. **红灯夹具先行**：先写会失败的测试再实现；存储层用真实 SQLite 临时库；
3. **顺序即依赖方向**：顺序错了会出现「契约加了 handler 没加 → dev FATAL」的
   中间态（resetAll 实证——fail-fast 反而在帮忙，但中间态本身要靠正确顺序避免）；
4. **每步验证**：targeted test → tsc → lint；verify:local 全量放最后，但门禁要
   **尽早暴露**，不攒到收尾；
5. **棘轮连锁预演**：file-size / functions / complexity 三门会拦合法增长
   （resetAll 三连拦实证）。二选一：拆分重构（正确但大动）或 --force 显式放宽
   （提交信息写明理由，非静默突破）。判断标准：声明性代码/注释 → 放宽可接受；
   逻辑复杂度 → 尽量拆。拆未拆的登记台账后续任务；
6. **契约闭环验证**：四处同步（meta / definitions / handler / mock）+ dev 启动
   实证（fail-fast 替你查漏）；
7. **提交规范**：Conventional Commits + 中文 body 三段（动机/方案/测试）；
   **主题不得以大写 token 开头**（subject-case 拦「MCP xxx」——resetAll 实测）；
8. **实施期变更传播（补丁①）**：实施中推翻设计假设时——① 设计文档对应节与
   状态节同步修订；② **边界变化必须回 CP1 重新拍板**；③ 台账登记「设计假设被
   推翻」的教训；
9. **收尾三件套**：设计文档状态节更新、修债必改台账（哈希/证据/新登记后续任务）、
   MEMORY.md 索引同步。

## 6. 发布与复盘

- 落地 ≠ 结束：按 §4.8 的指标与通道观察；experimental 内的功能按采用率决定转正；
- 复盘双锚：回审本流程（§7 迭代规则）+ 复盘功能自身（指标/反馈/诊断包）。

## 7. 方法论注记与迭代规则

本流程 = resetAll 单样本归纳 + 既有项目纪律的形式化。已知弱点：
多入口盘点（§4.9）与发布维度（§4.8）尚无第二样本验证。

**迭代规则**：每完成一个新功能，在 §3-§5 各加一行「本功能实测补充」；
三行以上仍未被任何功能命中的方向，下一版删除。本文件腐烂时，按台账
「台账腐烂方法论」同一纪律处理：修订并注明依据。
