前端状态管理架构设计
========================

版本: 2.19
日期: 2026-07-30（v2.19 Phase 8.18 dispatchTo 注入 items/live/seq，完全移除 statesRef 持久存储）
项目: Wails + Go 桌面应用

最终架构（v2.19 定稿）：statesRef 仅存 StateCore（不含 items/live/seq），dispatchTo 从 Zustand stores 注入后调用 reducer，执行后提取回存；14 个 per-tab Zustand store，PublicState = Omit<State, 32 fields>，外部可见 0 字段。

一、通信层设计（前端 ↔ 后端）
============================

1.1 二分原则
------------
按数据语义划分通信方式，不是按状态层级划分。

  通信方式                     承载的数据                   Wails API
  ──────────                   ───────────                 ───────────
  事件流（Events）             对话流式数据                 runtime.EventsOn
  绑定方法（Bindings）         持久化数据                   window.go.main.App.*

1.2 数据归属
------------

【事件流 - 对话数据】
├── 流式增量 delta
│   ├── text delta（助手回答增量）
│   ├── reasoning delta（推理过程增量）
│   ├── tool_dispatch（工具调用开始）
│   └── tool_progress（工具调用进度）
│
├── 交互请求
│   ├── approval_request（工具审批）
│   └── ask_request（用户选择）
│
└── 归档信号
    ├── turn_done（回合完成，携带完整数据）
    ├── usage（token 用量）
    └── compaction_done（压缩完成）

【API - 持久化数据】
├── 会话历史（hydrate/resume 时全量拉取）
├── checkpoints（检查点列表）
├── effort（思考强度配置）
├── meta（会话元信息）
├── tabs（标签页列表）
├── workspaces（工作区列表）
└── prompt history（提示词历史）


二、状态层设计（前端内部）
========================

2.1 三层洋葱模型
----------------

  层级          职责                数据特征              失效策略
  ────          ────                ──────                ──────
  L1 useState  组件局部 UI 状态     临时、与业务无关       组件卸载即销毁
  L2 Zustand   流式增量缓冲         高频、临时、API 拉不到  turn_done 后清空
  L3 TanStack  归档快照 + 持久化    可缓存、可恢复         invalidate + API
     Query

2.2 判断标准
------------

  数据是否需要"重新拉取"？
    ├── 需要     → TanStack Query（L3）
    └── 不需要   → Zustand（L2）

  数据是否与业务无关？
    ├── 无关     → useState（L1）
    └── 相关     → 走 L2 或 L3


三、L1 useState 归属
====================

原则：纯 UI 临时状态，与业务数据无关。

  状态                  说明
  ────                  ────
  菜单展开/折叠         dropdown、context menu
  hover 高亮            临时视觉反馈
  输入框临时值          composer 草稿（未提交）
  折叠面板状态          推理过程展开/收起
  滚动位置意图          "是否吸底"标记


四、L2 Zustand 归属
===================

原则：事件流临时缓冲，turn_done 后清空，不支持重新拉取。

4.1 流式增量缓冲（streaming-store）

  事件                Zustand 操作                    说明
  ────                ────────────                    ────
  text                append(itemId, text)            累积助手回答
  reasoning           appendReasoning(itemId, text)   累积推理过程
  tool_dispatch       setTool(itemId, tool)           工具调用开始
  tool_progress       updateTool(itemId, progress)    工具进度更新

4.2 交互请求（approval/ask）— useApprovalStore (L2 Zustand，per-tab 隔离)

  [v2.0 严格执行 2026-07-29] 推翻 v1.1 的"不迁移"结论，创建 useApprovalStore。
  [v2.1 per-tab 修订 2026-07-29] 全部 L2 业务 store（approval/turnLifecycle/usage）
    改为 per-tab 隔离，与 reducer Map<tabId, State> 结构对齐。
  迁移字段：approval, ask, promptArrivedAt, promptArrivedId, pendingPrompt,
            resolvedPromptId, promptEpoch, promptWaitStartedAt, turnWaitAccumMs

  per-tab 隔离的必要性（v2.1 实事求是分析）：
    1. reducer 用 Map<tabId, State>（useController line 1431-1433）为每个 tab 维护独立状态
    2. State 接口（line 120-201）包含 running/turnActive/approval/usage 等全部字段
    3. 注释（line 2-4）明确："background tabs preserve their streaming output, tool
       states, and approvals when the user switches away and back"
    4. 全局单例 store 只能持有一份 running/approval，切 tab 后丢失后台 tab 状态
    5. streaming-store 可全局单例（一次只有一个 tab 在流式），但 approval/turnLifecycle/
       usage 需要 per-tab（多 tab 可同时有 pending approval 或运行 turn）

  per-tab 实现模式（三个 store 一致）：
    - store 内部用 Record<tabId, PerTabState> 存储所有 tab 状态
    - 所有 action 接收 tabId 作为首参
    - 提供 useXxx(tabId) selector hook，undefined 时返回 EMPTY_PER_TAB 冻结常量
    - 提供 getXxxState(tabId) 供非 React 代码（事件路由器）调用
    - 提供 removeTab(tabId) 供 tab 关闭时释放内存

  时钟分离（v2.1 bug 修复，与原始 reducer 一致）：
    promptArrivedAt   ← promptEventClock()（performance.now()，单调时钟，
                        用于与 runtime 快照排序，#6429）
    promptWaitStartedAt ← Date.now()（墙钟，用于计算用户等待时长）
    两套时钟不可混用，否则 endPromptWait/clearAll 的 delta 计算错误。
    bug 根因：v2.0 setApproval/setAsk 用单个 now=promptEventClock() 同时设置
    两个字段，导致 promptWaitStartedAt 进入 performance.now() 时间域，
    而 clearAll 用 Date.now() 算 delta 得到错误差值。

  v1.1 理由验证（v2.0 实事求是分析）：
    v1.1 称"独立 store 会引入跨 store 同步问题"——此结论不成立：
      1. 所有事件处理集中在 useController 事件路由器
      2. 事件路由器可原子地调用多个 store 的 action
      3. React 18 批量更新保证同一事件循环内的 set 一起触发渲染
      4. 耦合点是事件处理级，不是字段语义级

  与 turn lifecycle 的协同（approval_request 事件）：
    approvalStore.setApproval(tabId, approval)   // 写 approval 专属字段
    turnLifecycleStore.setActive(tabId)           // 写 running/turnActive/cancellable=true

  联动清除点（事件路由器统一调度）：
    - turn_done:        approvalStore.clearAll(tabId)  (+ 保留 plan approval 特殊逻辑)
    - cancel_requested: approvalStore.clearAll(tabId)
    - unsend:           approvalStore.clearAll(tabId)
    - send_failed:      approvalStore.clearAll(tabId)

4.2.1 turn 生命周期 — useTurnLifecycleStore (L2 Zustand，per-tab 隔离)

  [v2.1 新增 2026-07-29] turn 生命周期 store，per-tab 隔离。
  迁移字段：running, turnActive, cancelRequested, cancellable, backgroundJobs,
            deliveryRecoveryActive, turnStartAt

  时钟：turnStartAt 用 Date.now()（与 currentTurnDurationMs 计算一致）。

  与 approvalStore 的协同（approval_request 事件）：
    turnLifecycleStore.setActive(tabId)
    approvalStore.setApproval(tabId, approval)

  与 usageStore 的协同（user 提交新 turn）：
    turnLifecycleStore.startTurn(tabId)
    approvalStore.resetTurnWait(tabId)
    usageStore.resetTurnUsage(tabId)

  turn_done 特殊逻辑：
    keepPlanApproval（exit_plan_mode）保留 running/turnActive/cancellable=true。
    调用方判断后调用 keepPlanApproval(tabId) 或 endTurn(tabId)。

4.2.2 token 用量累积 — useUsageStore (L2 Zustand，per-tab 隔离)

  [v2.1 新增 2026-07-29] usage 累积 store，per-tab 隔离。
  迁移字段：usage, turnTokens, turnTotalTokens, turnCost, turnArgChars,
            sessionTokens, sessionCost, sessionCurrency, usageSeq
  新增字段：contextUsed（store 内部计算，非 reducer State 迁移）

  累积计算逻辑在 store action 内部完成（与 reducer applyEvent "usage" case 等效）。
  countsTowardCurrentTurn（turnActive||running）判断由事件路由器完成，不在 store 内部：
    const ts = getTurnLifecycleState(tabId);
    if (ts.turnActive || ts.running) {
      usageStore.updateUsage(tabId, usage, contextWindow);
    }

    // 流式缓冲已归档，清空释放内存
    streamingStore.clearStreaming();

五、L3 TanStack Query 归属
==========================

原则：归档快照 + 持久化数据，支持 invalidate 和重新拉取。

5.1 双模式策略（v1.1 修正）

  [v1.1 修正 2026-07-29] 取消模式 A for turn_done 和 usage。

  模式 A（事件 payload 直接写 cache）适用条件严格：
    1. 事件 payload 必须包含完整的、可直接消费的数据
    2. 数据不涉及 reducer 内部的累积计算逻辑
    3. 数据与其他 reducer 字段无耦合

  实际评估结果：
    - turn_done：payload 不含完整 items 数据（WireEvent 无 items 字段），无法 setQueryData
    - usage：reducer 中有累积计算（turnTokens/sessionTokens/turnCost/sessionCost/usageSeq），
      setQueryData 无法替代这些累积逻辑
    - approval/ask：与 reducer 5+ 字段深度耦合（见 4.2 节）

  结论：当前项目无适合模式 A 的字段。所有 L3 数据均走模式 B（invalidate + API）。

  模式    触发条件                        数据来源                          适用场景
  ────    ──────                          ──────                            ──────
  模式 B  事件作信号，触发全量刷新         invalidate → API 拉取             所有 L3 数据

5.2 模式 B：invalidate + API（唯一模式）

  // turn_done 后失效历史缓存（触发 useConversationHistory 重新拉取）
  onEvent("turn_done", (e) => {
    invalidateHistoryCache(e.tabId);
    invalidateCheckpointsCache(e.tabId);
    invalidateEffortCache(e.tabId);
  });

  // hydrate / resume / tab 切换
  onEvent("hydrate_done", (e) => {
    invalidateHistoryCache(e.tabId);
    invalidateEffortCache(e.tabId);
  });

5.3 已知问题：turn_done 后的"间隙"

  问题：turn_done 后 clearStreaming（同步）立即清空流式缓冲，
  但 invalidateHistoryCache（异步）触发的 TQ 重新拉取需要时间。
  在 TQ 拉取完成前，useTranscriptItems 合并 hook 会显示旧的历史归档（不含最新 turn）。

  当前影响：无。Transcript 组件当前仍用 reducer state.items（未切换到 useTranscriptItems）。
  未来风险：当 Transcript 切换到 useTranscriptItems 时会暴露此问题。

  解决方案评估（v1.1 实事求是分析）：
    方案 A（延迟清空）：invalidateHistoryCache(tabId).then(() => clearStreaming())
      ❌ 不可行。边界问题：如果用户在 TQ 拉取期间发起新 turn，
      startStreaming 会创建新 item，但 TQ 拉取完成后的 clearStreaming()
      会清空所有 items（包括新 turn 的流式数据），破坏新 turn 的流式显示。

    方案 B（乐观写入 TQ cache）：从 reducer state.items 读取最终 items，
      转换为 HistoryPage 乐观写入 TQ cache
      ⚠️ 复杂。需处理 Item[] → HistoryMessage[] 转换和 id 体系差异。

    方案 C（推迟解决）：间隙问题推迟到 Transcript 切换时再解决
      ✅ 当前选择。理由：
      1. 间隙问题当前不影响用户（Transcript 用 state.items）
      2. Transcript 切换需要 20+ props 从 reducer 迁移，成本极高
      3. 在 Transcript 切换之前，解决间隙问题没有实际收益

  结论：间隙问题标记为"已知限制"，推迟到 Transcript 切换时一并解决。

5.5 meta/tabs/workspaces 评估结果（v2.2 修正）
---------------------------------------------

  [v2.2 修正 2026-07-29] meta 已迁移到 L3 TQ（Phase 6 完成）。

  meta（已迁移到 L3 TQ）：
    位置：原 useController reducer State.meta → TQ cache（useMeta）
    迁移方式（Phase 6）：
      6.1 ✅ useMetaQuery (L3)：useMeta hook + setOptimisticMeta + readMetaCache
      6.2 ✅ useController 双写机制：syncActionToStores 中 meta/optimistic_meta case
            通过 setOptimisticMeta 直接写入 TQ cache
      6.3 ✅ App.tsx 消费端切换：30+ 处 state.meta → metaFromTQ（useMeta hook）
      6.4 ✅ PublicState 排除 meta 字段：TypeScript 编译时检查外部误用
    v2.2 修正说明（不创建 useRuntimeStore）：
      v2.0 原计划将 meta 拆分为 L3 TQ（主体）+ L2 Zustand（runtime phase）。
      深度分析后发现不合理：
        1. runtime phase 不是事件流数据（runtime:rebuilt 事件只推送 epoch）
        2. 拆分破坏 Meta 完整性（ready 与 runtime.phase === "ready" 强耦合）
        3. useMeta.ts 已返回完整 Meta，再创建 useRuntimeStore 会导致数据源冲突
      修正方案：整个 Meta（含 runtime/startupErr）全部放入 L3 TQ 管理。
    双写机制：
      - meta action（来自 refreshMetaOnlyForTab → MetaForTab API）：setQueryData
      - optimistic_meta action（来自 metaFromTab 构造）：setQueryData
      - 不需要 invalidateMetaCache（所有 meta 更新场景都通过 dispatchTo meta action 更新 TQ cache）

  tabs（不迁移）：
    位置：useTabsStore（Zustand）— 已经在 L2 中
    状态：tabMetas、tabOrderIds、tabRevealSignal、transcriptRevealSignal、
          composerProfilesByTab、runtimeTransitionsByTab
    结论：已在 L2 Zustand，不属于 L3 TQ 迁移范围。

  workspaces（不迁移）：
    位置：App.tsx useState（line 850）
    类型：WorkspaceView[]
    用途：workspace 选择器的临时 UI 状态
    结论：纯 UI 临时状态，属于 L1 useState，不属于 L3 TQ 迁移范围。

十、核心原则（v2.2 修正）
=======================

  通信层二分：
    对话数据走事件流，持久化数据走 API。

  状态层三分：
    临时 UI 用 useState，流式增量用 Zustand，归档持久用 TanStack Query。

  关键修正（v2.2）：
    meta 的双写机制使用 setQueryData（类似模式 A），不走 invalidate + API。
    原因：meta action 的数据来源已经是 MetaForTab API 或 metaFromTab 构造的完整 Meta，
    setQueryData 可避免多余的 API 调用。
    其他 L3 数据（checkpoints/effort/messages）仍走模式 B（invalidate + API）。

  迁移完成的字段（v2.2）：
    - usage → L2 Zustand（per-tab，累积计算放 store action）
    - approval/ask → L2 Zustand（per-tab，5+ 字段耦合放 store action）
    - turnLifecycle → L2 Zustand（per-tab，running/turnActive 等）
    - meta → L3 TQ（整个 Meta，含 runtime/startupErr，setQueryData 双写）

  不迁移的边界（实事求是）：
    - tabs：已在 L2 Zustand（useTabsStore），不属于 L3 TQ 迁移范围
    - workspaces：L1 useState，纯 UI 临时状态

  注意：
    Zustand 和 TQ 是并列关系，不是串行关系。
    不存在"Zustand 把数据传给 TQ"这个动作。
    两者各自从事件流取自己关心的部分。
