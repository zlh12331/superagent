【文档定位】
本规范供 AI 编码代理在生成 Rust 代码时严格遵循。
基于 Rust 1.97、Edition 2024、Rust API Guidelines、Rust Style Guide、
Clippy lint 规则、Cargo Book、Tokio 1.52 文档、ANSSI 安全指南、
Rust Performance Book 等权威来源。
共 20 个章节，所有规则均为硬性约束。

【AI 执行原则】
  原则 A：本规范中的每一条都是硬性约束，违反任一条等于产生缺陷代码。
  原则 B：所有代码必须通过 `cargo fmt --all --check`、
          `cargo clippy --workspace --all-targets -- -D warnings`、
          `cargo test --workspace` 三重门禁。
  原则 C：如果某场景本规范未覆盖，选择最严格的做法并标注 [NEEDS CLARIFICATION]。
  原则 D：禁止使用"我觉得""可能""大概"等主观判断 — 一切由规则决定。
  原则 E：禁止使用 unwrap()/expect() 处理可能失败的操作（测试代码除外）。

【与已有规范的关系】
  - 本规范与 `typescript-dev-standards-ai.txt` 无冲突（不同语言）。
  - 本规范与 `software-architecture-principles-ai.txt` 无冲突（架构原则跨语言通用）。
  - 函数行数限制：统一为 40 行（与 TS 规范和架构规范一致）。
  - 测试覆盖率：≥85%（分支）/ ≥90%（语句）（与 TS 规范一致）。

================================================================================
  第一章  工具链配置（必须完整配置）
================================================================================

────────────────────────────────────────────────────────────────
  1.1  rust-toolchain.toml（必须存在）
────────────────────────────────────────────────────────────────

  每个项目根目录必须包含 `rust-toolchain.toml`，锁定工具链版本和组件：

    [toolchain]
    channel = "1.97.1"
    components = ["rustfmt", "clippy", "rust-src"]
    profile = "default"

  规则：
    1. channel 必须指定具体版本号（如 "1.97.1"），禁止用 "stable" 或 "nightly"
       （除非项目依赖 nightly 特性，需在注释中说明理由）。
    2. components 必须包含 "rustfmt" 和 "clippy"。
    3. 有 unsafe 代码的项目必须额外安装 "miri" 组件用于 CI。

────────────────────────────────────────────────────────────────
  1.2  Cargo.toml 模板（必须完整）
────────────────────────────────────────────────────────────────

    [package]
    name = "my-crate"
    version = "0.1.0"
    edition = "2024"
    rust-version = "1.97"
    authors = ["Author <author@example.com>"]
    description = "A concise description."
    license = "MIT OR Apache-2.0"
    repository = "https://github.com/user/my-crate"
    keywords = ["parser", "async"]
    categories = ["parsing"]

    [dependencies]
    serde = { version = "1.0", features = ["derive"] }
    tokio = { version = "1", features = ["full"] }
    thiserror = "2.0"
    tracing = "0.1"

    [dev-dependencies]
    pretty_assertions = "1.4"
    proptest = "1.11"
    criterion = "0.8"
    mockall = "0.15"

    [features]
    default = ["std"]
    std = []
    async-runtime = ["dep:tokio"]

    [profile.release]
    lto = "thin"
    codegen-units = 1
    strip = "symbols"

    [lints.clippy]
    enum_glob_use = "deny"
    unwrap_used = "deny"
    expect_used = "warn"
    pedantic = { level = "warn", priority = -1 }

  规则：
    1. edition 必须显式声明，新项目必须用 "2024"。
    2. rust-version（MSRV）必须显式声明。
    3. 依赖版本用默认 caret 简化语法（如 "1.0"），禁止裸 "*"，禁止过窄上限。
    4. [package] 元数据必须完整（license、repository、description）。
    5. workspace 项目必须用 [workspace.dependencies] 统一依赖版本。
    6. [lints.clippy] 必须在 Cargo.toml 中配置（不散落在代码属性中）。
    7. release profile 必须启用 lto = "thin"、codegen-units = 1、strip = "symbols"。
    8. 二进制 crate / 生产应用必须提交 Cargo.lock。库 crate 可不提交。

────────────────────────────────────────────────────────────────
  1.3  rustfmt.toml（必须存在）
────────────────────────────────────────────────────────────────

    edition = "2024"
    style_edition = "2024"
    max_width = 100
    use_small_heuristics = "Default"
    reorder_imports = true
    reorder_modules = true

  规则：
    1. edition 和 style_edition 必须显式设置为 "2024"。
       （直接运行 rustfmt 时默认 2015，不设置会导致格式不一致。）
    2. style_edition = "2024" 启用 Rust 2024 风格版格式化规则，
       包含 doctest 合并等性能优化。
    3. max_width 固定 100，不修改。
    4. CI 中必须运行 `cargo fmt --all --check` 作为硬性门禁。

    [advisories]

    [licenses]

    3. 许可证必须白名单限制。


================================================================================
  第二章  编码风格
================================================================================

  规则 2.1  缩进
    1. 使用 4 个空格缩进，禁止使用 Tab。
    2. 所有缩进必须是 4 的倍数。

  规则 2.2  行宽
    1. 每行不超过 100 个字符。
    2. 注释行不超过 80 个字符（含注释符号，不含缩进）。

  规则 2.3  Block 缩进优先
    1. 优先使用 block indent（换行后缩进），而非 visual indent（对齐到括号）。
    // 正确
    function_call(
        foo,
        bar,
    );
    // 错误
    function_call(foo,
                  bar);

  规则 2.4  尾随逗号
    1. 逗号分隔的列表中，换行后必须有尾随逗号。
    // 正确
    let array = [
        element,
        another_element,
    ];

  规则 2.5  空行
    1. item 和 statement 之间最多一个空行。
    2. 顶级 item 之间一个空行。
    3. 函数内部逻辑块之间零或一个空行。

  规则 2.6  导入排序
    1. use 语句在模块声明（mod）之前。
    2. use 语句按版本排序，self 和 super 排在最前。
    3. rustfmt 自动排序，禁止手动调整导入顺序。

  规则 2.7  属性规则
    1. 每个属性独占一行，缩进到 item 的层级。
    2. 只能有一个 #[derive(...)] 属性，多个 derive 合并：
       #[derive(Debug, Clone, PartialEq)]  // 正确
       // 禁止
       #[derive(Debug)]
       #[derive(Clone)]
    3. 带等号的属性，等号两侧各一个空格：#[foo = 42]。
    4. Rust 2024 Edition 中，no_mangle / export_name / link_section
       属性必须标记 unsafe：
       #[unsafe(no_mangle)]                // 正确（Edition 2024）
       // #[no_mangle]                     // 禁止（Edition 2024 中已废弃）

  规则 2.8  文档注释位置
    1. 文档注释 /// 必须放在属性 #[...] 之前。
    2. 优先使用行注释 ///，不使用块注释 /** ... */。
    3. 外部文档注释 /// 用于项文档，内部文档注释 //! 用于 crate/模块文档。

  规则 2.9  函数签名格式
    1. 标准顺序：[pub] [unsafe] [extern ["ABI"]] fn name(args) -> RetType
    2. 多行签名在开括号后断行，每个参数独占一行，尾随逗号：
       fn foo(
           arg1: i32,
           arg2: i32,
       ) -> i32 {
           ...
       }

  规则 2.10  Rust 2024 Edition 风格版
    1. rustfmt.toml 中 style_edition = "2024" 必须设置。
    2. 2024 风格版启用 doctest 合并（将多个 doctest 合并为单个测试函数），
       显著提升 cargo test --doc 的编译和运行性能。
    3. AI 生成的代码必须通过 `cargo +1.97 fmt --check` 验证。


================================================================================
  第三章  命名规范
================================================================================

  规则 3.1  大小写规则（RFC 430，必须 100% 遵循）

    ┌────────────────────┬──────────────────────┬──────────────────────┐
    │ 条目                │ 规范                  │ 示例                  │
    ├────────────────────┼──────────────────────┼──────────────────────┤
    │ 模块 (Modules)     │ snake_case           │ net_utils            │
    │ 类型 (Types)       │ UpperCamelCase       │ HttpClient           │
    │ Trait              │ UpperCamelCase       │ Display, FromIterator│
    │ Enum 变体           │ UpperCamelCase       │ ConnectionReset      │
    │ 函数 (Functions)   │ snake_case           │ parse_config         │
    │ 方法 (Methods)     │ snake_case           │ to_string            │
    │ 通用构造器          │ new / with_*         │ with_capacity        │
    │ 转换构造器          │ from_*               │ from_str             │
    │ 宏 (Macros)        │ snake_case!          │ println!, vec!       │
    │ 局部变量            │ snake_case           │ user_count           │
    │ 静态变量 (Statics) │ SCREAMING_SNAKE_CASE │ DEFAULT_TIMEOUT      │
    │ 常量 (Constants)   │ SCREAMING_SNAKE_CASE │ MAX_BUFFER_SIZE      │
    │ 类型参数            │ 简洁 UpperCamelCase  │ T, K, V              │
    │ 生命周期            │ 短 lowercase         │ 'a, 'de, 'src        │
    │ Feature            │ 直接用名称，无前缀    │ std（非 use-std）    │
    └────────────────────┴──────────────────────┴──────────────────────┘

  规则 3.2  缩写词规则
    1. UpperCamelCase 中，缩写词视为一个单词：Uuid（非 UUID），Usize（非 USize）。
    2. snake_case 中，缩写词全小写：is_xid_start。
    3. 单个字母不作为单词，除非是最后一个单词：btree_map（非 b_tree_map）。

  规则 3.3  转换方法命名（C-CONV）

    ┌──────────┬──────────┬───────────────────────────────────┐
    │ 前缀      │ 开销      │ 所有权变化                         │
    ├──────────┼──────────┼───────────────────────────────────┤
    │ as_      │ 免费      │ borrowed -> borrowed              │
    │ to_      │ 昂贵      │ borrowed -> borrowed/owned        │
    │ into_    │ 可变      │ owned -> owned (非 Copy)          │
    └──────────┴──────────┴───────────────────────────────────┘

    示例：
      str::as_bytes()        // &str -> &[u8], 零成本
      Path::to_str()         // &Path -> Option<&str>, 需 UTF-8 检查
      String::into_bytes()   // String -> Vec<u8>, 消费所有权

  规则 3.4  Getter 命名（C-GETTER）
    1. Rust 中 getter 不使用 get_ 前缀。
    // 正确
    impl S {
        pub fn first(&self) -> &First { &self.first }
        pub fn first_mut(&mut self) -> &mut First { &mut self.first }
    }
    // 错误
    pub fn get_first(&self) -> &First { ... }  // 禁止

    2. get 命名仅用于：存在单一且明显的可获取事物（如 Cell::get），
       或需要运行时验证（如边界检查）的 getter：
       fn get(&self, index: K) -> Option<&V>

  规则 3.5  迭代器方法命名（C-ITER）
    1. 迭代器方法名必须与返回类型匹配：
       fn iter(&self) -> Iter           // 返回 Iter
       fn iter_mut(&mut self) -> IterMut // 返回 IterMut
       fn into_iter(self) -> IntoIter   // 返回 IntoIter

  规则 3.6  错误类型词序（C-WORD-ORDER）
    1. 错误类型统一使用"动词-宾语-Error"词序：
       ParseIntError（非 IntParseError）
       JoinPathsError（非 PathsJoinError）

  规则 3.7  Crate 命名
    1. 禁止使用 -rs 或 -rust 作为前缀/后缀。
    2. Crate 名用 kebab-case（Cargo 惯例），代码中自动转为 snake_case。

  规则 3.8  Feature 命名
    1. Feature 名称不加 use-/with- 前缀，直接用名称。
       正确：std, async-runtime, tls
       错误：use-std, with-async, enable-tls
    2. 可选依赖用 dep: 前缀：async-runtime = ["dep:tokio"]。


================================================================================
  第四章  类型系统规则
================================================================================

  规则 4.1  Newtype 模式（C-NEWTYPE）
    1. 相同底层类型但不同语义必须用 newtype 区分：
       struct UserId(pub u64);
       struct PostId(pub u64);
       // 编译器阻止 UserId 和 PostId 混淆
    2. Newtype 零运行时开销。
    3. 为外部类型实现 trait 时（绕过孤儿规则）必须用 newtype。

  规则 4.2  禁止裸 bool 参数（C-CUSTOM-TYPE）
    1. 函数参数中禁止使用裸 bool，必须用枚举替代：
       // 正确
       let w = Widget::new(Small, Round);
       // 错误
       let w = Widget::new(true, false);  // true 是什么？false 是什么？

  规则 4.3  &str vs String vs &String
    ┌────────────────────────┬──────────┬──────────────────────────────┐
    │ 场景                    │ 使用      │ 原因                          │
    ├────────────────────────┼──────────┼──────────────────────────────┤
    │ 函数参数（只读）         │ &str     │ 接受 &String、&str、String 引用│
    │ 函数返回（借用）         │ &str     │ 零成本借用                    │
    │ 函数返回（拥有）         │ String   │ 需要所有权                    │
    │ 结构体字段（拥有）       │ String   │ 需要拥有数据                  │
    │ 结构体字段（借用）       │ &'a str  │ 零拷贝，但需生命周期          │
    │ 函数参数（需要拥有）     │ String   │ 明确表示消费所有权            │
    └────────────────────────┴──────────┴──────────────────────────────┘
    1. 永远不要在函数参数中使用 &String，用 &str 代替。

  规则 4.4  Arc vs Rc vs Box 决策树
    ┌─────────────────────────────┬──────────────────────────────────┐
    │ 场景                         │ 使用                              │
    ├─────────────────────────────┼──────────────────────────────────┤
    │ 堆分配，单一所有者            │ Box<T>                           │
    │ 单线程共享所有权              │ Rc<T>                            │
    │ 多线程共享所有权              │ Arc<T>                           │
    │ 单线程内部可变性              │ RefCell<T>                       │
    │ 多线程内部可变性（读写都锁）  │ Arc<Mutex<T>>                    │
    │ 多线程内部可变性（读多写少）  │ Arc<RwLock<T>>                   │
    └─────────────────────────────┴──────────────────────────────────┘
    1. 跨线程共享必须用 Arc，禁止用 Rc。
    2. 跨线程可变数据必须用 Mutex 或 RwLock 保护。

  规则 4.5  dyn vs 泛型（impl Trait）决策
    ┌──────────────┬─────────────────────┬──────────────────────────────┐
    │ 特性          │ 泛型 (impl Trait)   │ Trait Object (dyn Trait)     │
    ├──────────────┼─────────────────────┼──────────────────────────────┤
    │ 分派          │ 静态（编译期单态化） │ 动态（运行时虚函数表）        │
    │ 性能          │ 最优（零成本抽象）   │ 有虚函数调用开销              │
    │ 二进制大小    │ 可能增大             │ 更小                          │
    │ 类型异构      │ 不支持               │ 支持                          │
    │ 对象安全      │ 不需要               │ trait 必须是 object-safe     │
    └──────────────┴─────────────────────┴──────────────────────────────┘
    1. 默认用泛型（impl Trait），除非有明确理由用 dyn。
    2. 需要在一个集合中持有不同类型 → dyn Trait。
    3. 编译时间或二进制大小是瓶颈且类型变体多 → 考虑 dyn Trait。

  规则 4.6  生命周期标注
    1. 生命周期命名应简短：'a, 'b 为默认选择。
    2. 有语义含义时使用描述性名称：'src, 'de。
    3. 省略规则适用时不标注（编译器自动推断）。
    4. 省略规则不适用时必须显式标注。

  规则 4.7  Rust 2024 Edition: RPIT 生命周期捕获规则
    1. Edition 2024 中，`impl Trait` 返回类型默认捕获所有泛型参数和生命周期。
       （Edition 2021 中默认不捕获生命周期。）
    2. 使用 `use<..>` 精确控制捕获哪些参数：
       fn parse<'a>(input: &'a str) -> impl Parser + use<'a>;
    3. AI 在跨 Edition 迁移时必须注意此变化可能导致编译错误。
    4. 新代码中如需排除某些参数的捕获，使用精确控制语法。

  规则 4.8  PhantomData 使用
    1. 类型参数未被使用但需要在类型签名中声明时，用 PhantomData<T>。
    2. 表示类型逻辑上"拥有" T（即使运行时不存储）。
       use std::marker::PhantomData;
       struct Validator<T> {
           rules: Vec<Rule>,
           _marker: PhantomData<T>,
       }

  规则 4.9  Builder 模式（C-BUILDER）
    1. 数据结构构造复杂时（大量输入、可选配置）必须引入 Builder。
    2. 优先使用非消费 Builder（&mut self -> &mut Self）：
       impl Command {
           pub fn arg(&mut self, arg: String) -> &mut Command { ... ; self }
           pub fn spawn(&self) -> io::Result<Child> { ... }
       }

  规则 4.10  静态强制优于动态检查（C-VALIDATE）
    1. 强制机制优先级（从高到低）：
       a. 静态强制：选择能排除错误输入的参数类型（如用 Ascii 代替 u8）
       b. 动态强制：运行时验证，通过 panic! 或 Result 处理
       c. debug_assert! 强制：仅在 debug 构建中检查
       d. opt-out 强制：提供 _unchecked 变体


================================================================================
  第五章  所有权与借用
================================================================================

  规则 5.1  所有权原则
    1. 每个值有且只有一个所有者。
    2. 值在所有者离开作用域时被 drop。
    3. 转移所有权时原变量不再可用（非 Copy 类型）。

  规则 5.2  借用规则
    1. 任意时刻，要么有多个不可变借用，要么有一个可变借用，不能同时存在。
    2. 借用的生命周期不能超过被借用数据的生命周期。
    3. 函数参数优先用引用（&T / &mut T），除非需要所有权。

  规则 5.3  何时转移所有权
    1. 函数需要拥有数据（如存入结构体）→ 转移所有权（接收 T 或 String）。
    2. 函数只需要读取数据 → 借用（接收 &T 或 &str）。
    3. 函数需要修改数据 → 可变借用（接收 &mut T）。
    4. 函数返回新数据 → 转移所有权（返回 T）。

  规则 5.4  Clone 的使用限制
    1. 禁止无谓的 clone()：如果可以借用，不要 clone。
    2. clone() 必须有明确理由（如需要独立副本、需要转移所有权但原值仍需使用）。
    3. 大数据结构的 clone 必须在注释中说明理由。
    4. 实现 Clone 时必须在文档中说明 clone 的开销。

  规则 5.5  Copy trait
    1. 只有廉价的栈上类型（如 i32, bool, f64）才应实现 Copy。
    2. 包含堆数据的类型（如 String, Vec<T>）禁止实现 Copy。
    3. 实现了 Copy 的类型禁止有 Drop 实现。

  规则 5.6  Rust 2024 Edition: static mut 引用禁止
    1. Edition 2024 中，引用 static mut 变量为编译错误（默认 deny）。
    2. 替代方案：使用 std::sync::atomic 类型或 Mutex/RwLock。
    3. 如必须使用 static mut，通过 unsafe { &raw const / &raw mut } 访问。
    4. AI 生成的新代码禁止使用 static mut，必须用原子类型或同步原语替代。


================================================================================
  第六章  错误处理
================================================================================

  规则 6.1  thiserror vs anyhow 选型决策

    ┌──────────────┬──────────────────────┬──────────────────────────────┐
    │ 维度          │ thiserror             │ anyhow                       │
    ├──────────────┼──────────────────────┼──────────────────────────────┤
    │ 适用场景      │ 库代码 (library)      │ 应用代码 (application/binary)│
    │ 错误类型      │ 自定义专用错误类型    │ 单一动态错误类型             │
    │ 调用方信息    │ 精确控制              │ 不关心具体错误类型           │
    │ API 暴露      │ 不出现在公共 API 中   │ anyhow::Error 出现在返回类型 │
    │ 版本          │ 2.0.19                │ 1.0.104                      │
    └──────────────┴──────────────────────┴──────────────────────────────┘

    决策规则：
      1. 库代码必须使用 thiserror 2.0 定义专用错误类型。
      2. 应用代码（binary crate）使用 anyhow::Result<T>。
      3. 库的公共 API 中禁止出现 anyhow::Error。

  规则 6.2  thiserror 自定义错误类型
    1. 每个库必须定义自己的错误类型，使用 #[derive(Error, Debug)]。
    2. 每个变体必须有 #[error("...")] 描述，支持字段插值。
    3. 使用 #[from] 自动生成 From 实现。
    4. 错误类型词序遵循"动词-宾语-Error"（见规则 3.6）。

    示例：
      use thiserror::Error;

      #[derive(Error, Debug)]
      pub enum DataStoreError {
          #[error("data store disconnected")]
          Disconnect(#[from] io::Error),

          #[error("the data for key `{0}` is not available")]
          Redaction(String),

          #[error("invalid header (expected {expected:?}, found {found:?})")]
          InvalidHeader { expected: String, found: String },

          #[error("unknown data store error")]
          Unknown,
      }

  规则 6.3  anyhow 使用规则
    1. 应用代码中使用 anyhow::Result<T> 作为返回类型。
    2. 使用 ? 传播错误，无需手动 From 实现。
    3. 使用 .context() / .with_context() 附加上下文信息。
    4. 使用 bail! 宏提前返回错误。
    5. 禁止在库代码中使用 anyhow。

    示例：
      use anyhow::{Context, Result};

      fn get_cluster_info() -> Result<ClusterMap> {
          let config = std::fs::read_to_string("cluster.json")
              .context("Failed to read cluster config")?;
          let map: ClusterMap = serde_json::from_str(&config)?;
          Ok(map)
      }

  规则 6.4  Result vs Option 使用规则

    ┌──────────────┬──────────────────────┬──────────────────────────────┐
    │ 类型          │ 语义                  │ 使用场景                      │
    ├──────────────┼──────────────────────┼──────────────────────────────┤
    │ Option<T>    │ 值可能存在或不存在    │ 查找操作（HashMap::get）      │
    │ Result<T, E> │ 操作可能成功或失败    │ IO、解析、网络                │
    └──────────────┴──────────────────────┴──────────────────────────────┘

    1. 查询找不到返回 None，不返回 Err。
    2. 操作可能失败返回 Result。
    3. match Result 时必须穷尽匹配 Ok 和 Err。

  规则 6.5  ? 操作符
    1. 优先使用 ? 传播错误，不手动 match。
    2. ? 自动调用 From 进行错误类型转换。
    3. 配合 anyhow 时无需手动实现 From。
    4. 配合 thiserror 时使用 #[from] 自动生成 From。

  规则 6.6  panic vs Result 决策

    使用 panic! 的场景（仅限以下）：
      1. 不变量被违反（程序逻辑错误，非外部输入错误）。
      2. 不可能到达的代码分支（配合 unreachable!()）。
      3. 数组越界等编程错误。
      4. 析构函数中绝不 panic（C-DTOR-FAIL）。

    使用 Result 的场景（除上述外全部）：
      1. 任何外部输入导致的失败（IO、网络、解析）。
      2. 用户提供的参数验证。
      3. 资源获取失败。
      4. 库代码中应优先返回 Result 而非 panic。

  规则 6.7  unwrap() / expect() 使用规则

    允许使用的场景（仅限以下）：
      1. 测试代码中。
      2. 文档示例中（但优先用 ? 代替 unwrap）。
      3. 确定不可能失败的硬编码场景（如 "123".parse::<i32>()）。

    禁止使用的场景：
      1. 生产代码中处理外部输入（IO、网络、用户输入）。
      2. 库代码的公共 API 中。
      3. 任何可能因外部因素失败的操作。

    规则：
      1. CI 中 clippy::unwrap_used 必须设为 deny。
      2. clippy::expect_used 必须设为 warn。
      3. 当确实需要使用时，用 expect("msg") 替代 unwrap()，提供上下文信息。

  规则 6.8  析构函数规则（C-DTOR-FAIL, C-DTOR-BLOCK）
    1. Drop 实现中绝不 panic（panic 中的析构失败会导致 abort）。
    2. Drop 实现中不执行阻塞操作。
    3. 需要失败处理的资源释放，提供单独的 close() 方法返回 Result，
       Drop 实现中忽略或记录错误。

  规则 6.9  函数行数限制
    1. 函数体不超过 40 行（与 TS 规范和架构规范一致）。
    2. 超过 40 行检查是否违反 SRP，提取子函数。


================================================================================
  第七章  模块组织
================================================================================

  规则 7.1  可见性规则
    1. pub：完全公开，对外可见。
    2. 无修饰：仅当前模块及子模块可见。
    3. pub(crate)：crate 内可见，不暴露给外部。用于库的内部 API。
    4. pub(super)：仅父模块可见。
    5. pub(in path)：仅在指定路径范围内可见。

    规则：
      1. 内部项必须用 pub(crate)，禁止对无法逃出 crate 的项使用裸 pub。
      2. 公共 API 必须通过 lib.rs 的 pub use 扁平化导出，隐藏内部模块结构。
      3. 最小可见性原则：能用 pub(crate) 就不用 pub。

  规则 7.2  重导出（pub use）
    1. 通过 lib.rs 中的 pub use 扁平化公共 API：
       pub mod io;
       pub use io::Read;  // 用户可直接 my_crate::Read
    2. 深层模块的公共项必须在 crate 根重导出。

  规则 7.3  Prelude 模式
    1. 大型 crate 可提供 prelude 模块导出常用符号：
       pub mod prelude {
           pub use crate::types::{Config, Error, Result};
           pub use crate::client::Client;
       }
    2. 用户按惯例 use my_crate::prelude::*; 引入。

  规则 7.4  Feature Flags
    1. Feature 名称不加 use-/with- 前缀，直接用名称（如 std 而非 use-std）。
    2. 可选依赖用 dep: 前缀：async-runtime = ["dep:tokio"]。
    3. Feature 必须在 Cargo.toml 的 [features] 表中定义。

  规则 7.5  Crate 级文档
    1. lib.rs 顶部必须有 //! crate 级文档。
    2. 说明 crate 用途并含示例。


================================================================================
  第八章  项目结构
================================================================================

  规则 8.1  标准目录结构（必须遵循）

    .
    ├── Cargo.toml
    ├── Cargo.lock          # 二进制 crate 必须提交
    ├── rust-toolchain.toml  # 必须存在
    ├── rustfmt.toml         # 必须存在
    ├── deny.toml            # 必须存在
    ├── src/
    │   ├── lib.rs           # 库 crate 入口
    │   ├── main.rs          # 二进制 crate 入口
    │   └── bin/             # 额外可执行文件
    ├── tests/               # 集成测试（测试公共 API）
    ├── benches/             # 基准测试
    └── examples/            # 示例

    注意：此目录结构适用于标准 Rust 项目。若采用六边形/洋葱架构
    （见架构规范 §2-3），src/ 内部结构应按领域/端口/适配器组织。

  规则 8.2  模块文件组织
    1. 使用 Rust 2018+ 约定：foo.rs + foo/ 目录，禁止新代码使用 mod.rs。
    2. 禁止同时存在 foo.rs 和 foo/mod.rs。

    // 目录结构
    src/
    ├── lib.rs      // mod util;
    ├── util.rs     // mod config;
    └── util/
        └── config.rs

  规则 8.3  测试组织
    1. 单元测试：内联在 #[cfg(test)] mod tests 中，测试私有函数。
    2. 集成测试：放在 tests/ 目录，每个文件是独立 crate，测试公共 API。
    3. 文档测试：写在 /// 注释的代码块中。
    4. Edition 2024 中 doctest 自动合并为单个测试函数，提升编译性能。
       AI 无需修改 doctest 写法，编译器自动优化。

  规则 8.4  Cargo Workspace
    1. 多 crate 项目必须用 workspace 组织。
    2. 共享同一个 Cargo.lock 和 target 目录。
    3. 依赖版本通过 [workspace.dependencies] 统一管理。
    4. workspace 根 Cargo.toml 示例：

       [workspace]
       members = ["crates/*"]
       resolver = "3"

       [workspace.dependencies]
       serde = { version = "1.0", features = ["derive"] }
       tokio = { version = "1", features = ["full"] }
       thiserror = "2.0"

    5. resolver = "3" 是 Edition 2024 的默认 resolver，必须显式声明。


================================================================================
  第九章  异步编程
================================================================================

  规则 9.1  运行时选择
    1. 新项目默认使用 Tokio 1.52 作为异步运行时。
    2. 除非用户明确指定其他运行时（如 async-std、smol）。
    3. Tokio 1.51+ 稳定了 LocalRuntime（单线程运行时），适用于
       不需要多线程的轻量场景。
    4. io_uring 支持仍为不稳定特性，生产环境暂不使用。

  规则 9.2  spawn vs spawn_blocking
    1. tokio::spawn：用于非阻塞异步任务。
    2. tokio::task::spawn_blocking：用于阻塞操作（同步 IO、CPU 密集计算、同步 C 库）。
    3. 禁止在 async 上下文中直接执行阻塞操作。

    示例：
      // 异步非阻塞任务
      tokio::spawn(async { /* 异步工作 */ });

      // 阻塞操作
      let result = tokio::task::spawn_blocking(|| {
          // 阻塞操作或 CPU 密集计算
          "blocking completed"
      }).await?;

  规则 9.3  async fn in traits
    1. 私有 trait：可直接使用 async fn。
    2. 公开 trait：禁止使用裸 async fn（无法指定 Send bound）。
       必须使用 #[trait_variant::make] 或显式声明 -> impl Future<Output = T> + Send。
    3. 需要 dyn Trait（动态分发）：使用 #[async_trait] 宏。

    示例（使用 trait_variant 0.1.x）：
      // 公开 trait：使用 trait-variant 生成 Send 变体
      #[trait_variant::make(HttpService: Send)]
      pub trait LocalHttpService {
          async fn fetch(&self, url: Url) -> HtmlBody;
      }
      // HttpService 自动获得 Send bound，可被 tokio::spawn 使用

  规则 9.4  Rust 2024: async 闭包
    1. Edition 2024 / Rust 1.85+ 稳定了 async 闭包语法。
    2. async 闭包捕获环境变量的行为与同步闭包一致。
       let fetcher = async |url: String| { /* async work */ };
    3. AI 在需要传递异步回调时，优先使用 async 闭包而非手动构建 Future。

  规则 9.5  Send/Sync bounds
    1. 在多线程运行时中 spawn 的任务，其 Future 必须 Send。
    2. trait 中的 async 方法返回的 Future 不带 Send bound 时，
       tokio::spawn 会编译失败。

  规则 9.6  select! 宏与取消安全
    1. 在循环中使用 select! 时，必须确保每个分支取消安全。

    取消安全的方法（可以在 select! 循环中使用）：
      - mpsc::Receiver::recv
      - broadcast::Receiver::recv
      - watch::Receiver::changed
      - TcpListener::accept
      - AsyncReadExt::read / read_buf
      - AsyncWriteExt::write / write_buf
      - StreamExt::next

    不取消安全的方法（禁止在 select! 循环中使用，会导致数据丢失）：
      - AsyncReadExt::read_exact
      - AsyncReadExt::read_to_end / read_to_string
      - AsyncWriteExt::write_all
      - tokio::sync::Mutex::lock / RwLock::read / RwLock::write

    2. 对于不取消安全的方法，必须添加注释说明风险或改用取消安全的替代方案。

  规则 9.7  Pin/Unpin
    1. 要 .await 一个引用，被引用的值必须被 pin 或实现 Unpin。
    2. 使用 tokio::pin! 进行栈上 pinning。
    3. 使用 Box::pin 进行堆上 pinning。

  规则 9.8  所有异步操作必须设置超时
    1. 所有异步操作（网络请求、数据库查询、消息队列）必须设置超时。
    2. 使用 tokio::time::timeout 包装。
    3. 超时后必须清理资源。

    示例：
      use tokio::time::{timeout, Duration};

      match timeout(Duration::from_secs(30), fetch_data()).await {
          Ok(result) => result?,
          Err(_) => return Err(TimeoutError.into()),
      }


================================================================================
  第十章  并发编程
================================================================================

  规则 10.1  Send + Sync
    1. Send：类型可以安全地在线程间转移所有权。
    2. Sync：类型可以通过 &T 在线程间安全共享。
    3. 跨线程共享必须用 Arc，禁止用 Rc。
    4. 跨线程共享可变数据必须用 Mutex 或 RwLock 保护。

    重要例外（非 Send 或非 Sync）：
      - Rc<T>：既非 Send 也非 Sync
      - Cell<T> / RefCell<T>：非 Sync
      - MutexGuard<T>：非 Send（锁必须在获取它的线程释放）

  规则 10.2  Arc/Mutex/RwLock 使用规则

    ┌─────────────────────────────┬──────────────────────┐
    │ 场景                         │ 推荐类型              │
    ├─────────────────────────────┼──────────────────────┤
    │ 多线程共享只读数据            │ Arc<T>               │
    │ 多线程共享可变数据            │ Arc<Mutex<T>>        │
    │ 读多写少场景                  │ Arc<RwLock<T>>       │
    └─────────────────────────────┴──────────────────────┘

    1. 锁持有时间必须最小化。
    2. 禁止在锁内调用外部服务或执行 IO。
    3. 锁内禁止 await（禁止持有 MutexGuard 跨 await 点）→ 用 tokio::sync::Mutex。

  规则 10.3  通道选择

    ┌──────────────────────┬──────────────────────────────────────┐
    │ 通道类型              │ 适用场景                              │
    ├──────────────────────┼──────────────────────────────────────┤
    │ std::sync::mpsc       │ 标准库同步通道，单生产者多消费者      │
    │ crossbeam 0.8.4       │ 高性能多生产者多消费者，支持 select!  │
    │ flume 0.12.0          │ 易用的高性能通道                      │
    │ tokio::sync::mpsc     │ 异步通道，与 Tokio 运行时集成         │
    └──────────────────────┴──────────────────────────────────────┘

  规则 10.4  竞争条件预防
    1. Rust 类型系统在编译时防止数据竞争，但不能防止所有竞争条件。
    2. 逻辑竞争条件（如 TOCTOU）需通过正确的锁粒度和原子操作预防。
    3. 共享可变数据时必须在注释中说明锁的粒度和持有时间。


================================================================================
  第十一章  unsafe 与安全
================================================================================

  规则 11.1  unsafe 使用限制
    1. unsafe 关键字仅解锁五种操作：
       a. 解引用裸指针（*const T / *mut T）
       b. 调用 unsafe fn
       c. 访问可变 static 变量
       d. 访问 union 字段
       e. 实现 unsafe trait
    2. AI 生成的代码默认禁止使用 unsafe，除非有明确且必要的理由。
    3. 使用 unsafe 时必须在代码审查中标注 [NEEDS REVIEW: unsafe]。

  规则 11.2  SAFETY 注释（必须）
    1. 每个 unsafe 块必须携带 // SAFETY: 注释。
    2. 注释需列出所有验证的不变式（invariants）。
    3. 如果审查者无法验证注释，代码必须被拒绝。

    示例：
      fn read_value(ptr: *const i32) -> Option<i32> {
          if ptr.is_null() {
              return None;
          }
          Some(unsafe {
              // SAFETY:
              // 1. ptr is non-null (checked above).
              // 2. Caller guarantees ptr points to an initialized, aligned i32.
              // 3. No concurrent writes occur to this address.
              *ptr
          })
      }

  规则 11.3  安全抽象模式
    1. 将 unsafe 隔离在最小范围内。
    2. 在外部提供 safe API。
    3. 验证逻辑放在 unsafe 块外面。

  规则 11.4  FFI 安全
    1. FFI 边界必须捕获所有 panic（使用 std::panic::catch_unwind）。
    2. 从 Rust 向外部代码展开（unwinding）会导致未定义行为（UB）。
    3. 跨越 FFI 边界的指针必须保持 Rust 的内存模型。

    示例（Edition 2024 unsafe extern 语法）：
      // Edition 2024: extern 块需要 unsafe 关键字
      unsafe extern "C" {
          fn external_function(input: *const u8, len: usize) -> i32;
      }

      // Edition 2024: no_mangle 需要 unsafe 标记
      #[unsafe(no_mangle)]
      pub extern "C" fn ffi_function(input: *const u8, len: usize) -> i32 {
          let result = std::panic::catch_unwind(|| {
              do_work(input, len)
          });
          match result {
              Ok(v) => v,
              Err(_) => -1,  // panic 时返回错误码，不展开
          }
      }

  规则 11.5  整数溢出处理
    1. Debug 模式：整数溢出 panic。
    2. Release 模式：整数溢出执行二进制补码环绕，不 panic。
    3. 安全敏感代码（文件大小、缓冲区长度、权限检查）必须使用 checked_* 或 saturating_*。
    4. 禁止依赖 release 模式的隐式环绕行为。

    示例：
      let result = a.checked_add(b);      // 返回 Option<T>
      let saturated = a.saturating_add(b); // 饱和加法
      let wrapped = a.wrapping_add(b);     // 显式环绕

  规则 11.6  供应链安全
    1. CI 必须包含 cargo audit 0.22.2（扫描 RustSec 漏洞数据库）。
    2. CI 必须包含 cargo deny check 0.20.1（许可证策略、禁止 crate、重复依赖）。
    3. 可选：cargo vet（供应链验证）、cargo-auditable（嵌入依赖审计信息）。
    4. build.rs 和 proc macro 可执行任意代码，必须审查。
    5. 有 unsafe 代码的项目必须在 CI 中加入 Miri 检查。

  规则 11.7  Rust 2024 Edition 安全变化（全部强制遵守）
    1. unsafe extern 块：extern 块必须标记 unsafe 关键字。
       // 正确（Edition 2024）
       unsafe extern "C" { fn foo(); }
       // 错误（Edition 2024 中编译失败）
       extern "C" { fn foo(); }

    2. unsafe 属性：no_mangle / export_name / link_section 必须标记 unsafe。
       #[unsafe(no_mangle)]           // 正确
       #[unsafe(export_name = "foo")] // 正确
       #[no_mangle]                   // 错误（Edition 2024 中警告）

    3. unsafe_op_in_unsafe_fn：默认警告（Edition 2024）。
       unsafe fn 内部的 unsafe 操作必须显式包裹在 unsafe 块中。

    4. 禁止引用 static mut：默认 deny 错误。
       必须使用原子类型（AtomicU64 等）或 Mutex/RwLock 替代。

    5. std::env::set_var / remove_var 变为 unsafe：
       在多线程环境中调用这些函数是不安全的。
       AI 必须在 unsafe 块中调用，并添加 SAFETY 注释。

    6. gen 关键字保留：禁止将 gen 用作标识符。

  规则 11.8  Rust 1.95-1.97 新特性（AI 必须了解并使用）
    1. Rust 1.95 — cfg_select! 宏稳定：
       替代 cfg-if crate，条件编译优先使用 cfg_select!。
       示例：
         cfg_select! {
             target_os = "linux" => { fn syscall() { /* ... */ } }
             target_os = "windows" => { fn syscall() { /* ... */ } }
             _ => { fn syscall() { /* ... */ } }
         }

    2. Rust 1.95 — match 中 if let 守卫：
       简化嵌套匹配，可在 match 分支中使用 if let 作为守卫。
       示例：
         match value {
             Some(x) if let Some(y) = x.inner => { /* ... */ }
             _ => {}
         }

    3. Rust 1.96 — 新 Range 类型（RFC 3550）：
       引入 RangeFrom、RangeTo 等改进类型，增强范围表达式能力。

    4. Rust 1.96 — assert_matches! 宏稳定：
       简化模式匹配断言，测试中优先使用。
       示例：
         assert_matches!(result, Ok(42));

    5. Rust 1.97 — Symbol mangling v0 默认启用：
       无需手动配置，改进调试信息和链接器错误消息。

    6. Rust 1.97 — CARGO_BUILD_WARNINGS=deny：
       Cargo 原生支持将编译警告转为错误，不使构建缓存失效。
       替代 RUSTFLAGS="-D warnings"（后者会使增量编译缓存失效）。
       CI 中推荐使用：
         CARGO_BUILD_WARNINGS=deny cargo clippy --workspace --all-targets --keep-going

    7. Rust 1.97 — linker_messages lint：
       链接器输出不再默认隐藏，便于调试链接问题。


================================================================================
  第十二章  性能
================================================================================

  规则 12.1  分配避免
    1. 函数参数优先使用 &str、&[T] 而非 String、Vec<T>（除非需要所有权）。
    2. 使用迭代器代替 collect() 后再遍历：
       // 不好
       let v: Vec<i32> = iter.map(|x| x * 2).collect();
       let sum: i32 = v.iter().sum();
       // 好
       let sum: i32 = iter.map(|x| x * 2).sum();

    3. Box<str> 优于 Box<String>（节省一个指针大小的内存）。
    4. 大结构体字段可 Box 化以减小类型大小，改善缓存局部性。

  规则 12.2  Vec 容量提示
    1. 已知或能估计元素数量时，必须使用 Vec::with_capacity(n)。
       // 好
       let mut v = Vec::with_capacity(1000);
       for i in 0..1000 { v.push(i); }
       // 不好
       let mut v = Vec::new();
       for i in 0..1000 { v.push(i); }

  规则 12.3  构建配置优化
    1. release profile 必须配置：
       [profile.release]
       lto = "thin"        # 全程序优化
       codegen-units = 1   # 最大优化
       strip = "symbols"   # 去除符号

    2. 可选（根据项目需求）：
       panic = "abort"     # 减小二进制大小
       opt-level = "z"     # 最小化二进制大小

  规则 12.4  零成本抽象验证
    1. Rust 的零成本抽象：不为你没有使用的功能付费；你使用的功能无法手写更好。
    2. 验证方法：使用 cargo asm 查看生成的汇编代码。

  规则 12.5  性能分析工具
    1. cargo flamegraph：生成火焰图，可视化 CPU 时间分布。
    2. Criterion 0.8.0：精密基准测试框架，统计显著性分析。
    3. hyperfine：通用命令行基准测试工具。


================================================================================
  第十三章  测试
================================================================================

  规则 13.1  单元测试约定
    1. 单元测试使用 #[cfg(test)] mod tests 内联在源文件中。
    2. 测试私有函数和内部逻辑。
    3. 测试函数命名必须清晰描述被测行为：
       fn test_empty_vec_returns_none（非 test1）。

    示例：
      pub fn add_two(a: i32) -> i32 { a + 2 }

      #[cfg(test)]
      mod tests {
          use super::*;

          #[test]
          fn it_adds_two() {
              assert_eq!(add_two(2), 4);
          }
      }

  规则 13.2  集成测试约定
    1. 集成测试放在 tests/ 目录，每个文件编译为独立 crate。
    2. 仅测试 crate 的公共 API。
    3. 共享测试辅助代码放 tests/common/mod.rs。

  规则 13.3  assert 约定
    1. assert_eq!(actual, expected)：比较相等性。
    2. assert!(condition)：验证布尔条件。
    3. assert_ne!(a, b)：验证不等。
    4. Rust 1.96+ 可使用 assert_matches! 验证模式匹配：
       assert_matches!(result, Ok(42));

  规则 13.4  #[should_panic] 使用
    1. 验证函数在特定条件下 panic。
    2. 必须使用 expected 参数匹配 panic 消息：
       #[test]
       #[should_panic(expected = "index out of bounds")]
       fn test_out_of_bounds() { ... }

  规则 13.5  属性测试（Property-Based Testing）
    1. 使用 proptest 1.11.0 进行属性测试。
    2. 自动生成大量随机输入验证不变式。

    示例：
      proptest! {
          #[test]
          fn test_addition_commutative(
              a in i32::MIN..i32::MAX,
              b in i32::MIN..i32::MAX
          ) {
              prop_assert_eq!(a.wrapping_add(b), b.wrapping_add(a));
          }
      }

  规则 13.6  基准测试
    1. 使用 Criterion 0.8.0 进行基准测试（禁止使用不稳定内置 benchmark）。
    2. 使用 black_box 防止编译器优化掉被测代码。

    示例：
      use criterion::{black_box, criterion_group, criterion_main, Criterion};

      fn benchmark_fibonacci(c: &mut Criterion) {
          c.bench_function("fib 20", |b| {
              b.iter(|| fibonacci(black_box(20)))
          });
      }
      criterion_group!(benches, benchmark_fibonacci);
      criterion_main!(benches);

  规则 13.7  Mock 模式
    1. 使用 mockall 0.15.0 库进行 trait mock。
    2. 通过 #[automock] 自动生成 mock 实现。

  规则 13.8  测试覆盖率
    1. 语句覆盖率 ≥90%，分支覆盖率 ≥85%，函数覆盖率 ≥90%。
    2. 使用 cargo-llvm-cov 0.5.17 测量覆盖率（推荐）或 cargo-tarpaulin。
    3. CI 中覆盖率不达标必须失败。
    4. 生成覆盖率报告命令：
       cargo llvm-cov --workspace --all-features --lcov --output-path lcov.info

  规则 13.9  Doctest
    1. 每个公开函数必须有 doctest 示例。
    2. doctest 中必须用 ? 处理错误，禁止 unwrap（C-QUESTION-MARK）。
    3. CI 中通过 cargo test --doc 执行 doctest。
    4. Edition 2024 中 doctest 自动合并，编译性能显著提升，
       AI 无需改变 doctest 写法。


================================================================================
  第十四章  文档
================================================================================

  规则 14.1  文档注释语法
    1. ///（外层文档注释）：文档化其之后的项（函数、结构体、枚举等）。
    2. //!（内层文档注释）：文档化其所在的项（crate 级文档放 lib.rs 顶部）。
    3. 优先使用行注释 ///，不使用块注释 /** ... */。

  规则 14.2  文档示例（Doctest）
    1. 所有公共项必须有 /// 文档注释并含 # Examples 段（C-EXAMPLE）。
    2. 示例展示"为什么用"而非仅"怎么调"。
    3. 文档示例必须用 ? 处理错误，禁止 unwrap/expect（C-QUESTION-MARK）。
    4. 隐藏行用 # 开头（如 # use std::error::Error;）。

    示例：
      /// Adds two numbers together.
      ///
      /// # Examples
      ///
      /// ```
      /// use my_crate::add;
      ///
      /// assert_eq!(add(2, 3), 5);
      /// ```
      pub fn add(a: i32, b: i32) -> i32 { a + b }

  规则 14.3  文档化 Errors、Panics、Safety
    1. 可能返回错误的函数必须文档化 # Errors 段：
       /// # Errors
       /// Returns an error if the connection is lost.

    2. 可能 panic 的函数必须文档化 # Panics 段：
       /// # Panics
       /// Panics if `index` is out of bounds.

    3. 所有 unsafe 函数必须文档化 # Safety 段，说明调用者责任：
       /// # Safety
       /// Caller must ensure `ptr` is valid and aligned.

  规则 14.4  Intra-doc 链接
    1. 使用 [`Type`] 语法自动解析为该类型的文档页。
    2. 必须启用 #![deny(rustdoc::broken_intra_doc_links)] 确保链接有效。

  规则 14.5  #[doc(hidden)] 用法
    1. 对用户无意义的实现细节必须用 #[doc(hidden)] 或 pub(crate) 隐藏。
    2. 禁止在公共 API 中暴露内部实现细节。

  规则 14.6  代码块属性
    1. ignore：忽略（不编译不运行），适合伪代码。
    2. should_panic：应编译但运行时 panic。
    3. no_run：编译但不运行（如需网络的示例）。
    4. compile_fail：应编译失败（演示错误用法）。


================================================================================
  第十五章  API 设计
================================================================================

  规则 15.1  Rust API 不遵循稳健性原则（C-VALIDATE）
    1. Rust API 应尽可能强制输入有效性，而非"发送时保守，接收时宽容"。
    2. 强制机制优先级：静态 > 动态 > debug_assert! > opt-out。

  规则 15.2  类型安全优先（C-NEWTYPE, C-CUSTOM-TYPE）
    1. 相同底层类型不同语义必须用 newtype 区分。
    2. 禁止裸 bool 参数，用枚举替代。
    3. 优先使用能排除错误输入的参数类型。

  规则 15.3  构造器命名（C-COMMON）
    1. 通用构造器用 new。
    2. 带参数的构造器用 with_*：with_capacity, with_config。
    3. 转换构造器用 from_*：from_str, from_bytes。

  规则 15.4  转换方法命名（C-CONV）
    1. as_*：零成本借用转换（borrowed -> borrowed）。
    2. to_*：有成本的同层转换。
    3. into_*：消费所有权的转换（owned -> owned）。
    4. from_*：从其他类型构造。

  规则 15.5  迭代器方法（C-ITER, C-ITER-TY）
    1. iter() -> Iter：不可变迭代器。
    2. iter_mut() -> IterMut：可变迭代器。
    3. into_iter() -> IntoIter：消费迭代器。
    4. 迭代器类型名称必须与产生它们的方法匹配。

  规则 15.6  向后兼容
    1. 新增字段：必须是 Option<T> 或有默认值。
    2. 删除字段：先标记 #[deprecated]，等所有消费方升级后再删除。
    3. 修改字段类型：禁止，新增新字段代替。
    4. SemVer 规则：pre-1.0 的 minor 版本允许 breaking change。

================================================================================
  第十八章  日志规范
================================================================================

  规则 18.1  日志库选择
    1. 使用 tracing 0.1.44 库（非 log 库），支持结构化日志和异步。
    2. 使用 tracing-subscriber 配置日志输出。

  规则 18.2  日志级别
    1. ERROR：系统错误，需要立即处理。必须包含完整错误堆栈。
    2. WARN：潜在问题，不影响当前操作。
    3. INFO：关键业务节点（启动、关闭、关键操作完成）。
    4. DEBUG：调试信息，生产环境关闭。
    5. TRACE：详细执行流程，生产环境关闭。

  规则 18.3  日志内容
    1. 每条日志包含：时间戳、级别、模块名、消息、结构化字段。
    2. 错误日志必须包含完整错误链（使用 ? 传播时自动包含）。
    3. 关键节点记录 INFO 日志：函数入口和出口、关键业务操作、外部调用请求和响应。
    4. 禁止记录密码、密钥、个人隐私信息。
    5. 禁止在高频循环中写日志。

  规则 18.4  tracing 使用
    1. 使用 #[tracing::instrument] 自动记录函数入口和参数。
    2. 使用 span 记录请求上下文。
    3. 使用 structured fields 而非字符串拼接：
       // 正确
       tracing::info!(user_id = %user.id, "User logged in");
       // 错误
       tracing::info!("User {} logged in", user.id);


================================================================================
  第十九章  AI 代码生成检查清单
================================================================================

  AI 在生成 Rust 代码后，必须逐项自检：

  【类型安全】
  □ 函数参数中字符串类型是否用 &str 而非 &String？
  □ 函数参数中数组类型是否用 &[T] 而非 &Vec<T>？
  □ 是否避免了裸 bool 参数（用枚举替代）？
  □ 相同底层类型不同语义是否用了 newtype？
  □ 默认用泛型而非 dyn（除非需要异构集合）？
  □ 跨线程共享是否用了 Arc 而非 Rc？

  【错误处理】
  □ 库代码是否用了 thiserror 2.0 定义错误类型？
  □ 应用代码是否用了 anyhow::Result？
  □ 生产代码中是否禁止了 unwrap()/expect()？
  □ 是否用 ? 传播错误而非手动 match？
  □ 析构函数中是否有 panic 或阻塞操作？
  □ 可能 panic 的函数是否文档化了 # Panics？
  □ 可能返回错误的函数是否文档化了 # Errors？

  【unsafe 与安全】
  □ 每个 unsafe 块是否有 // SAFETY: 注释？
  □ unsafe 是否隔离在最小范围内（安全抽象模式）？
  □ FFI 边界是否捕获了所有 panic？
  □ FFI 边界是否使用了 unsafe extern 语法（Edition 2024）？
  □ 属性是否使用了 unsafe 标记（#[unsafe(no_mangle)]，Edition 2024）？
  □ 安全敏感整数运算是否用了 checked_*？
  □ 是否禁止了 static mut 引用（Edition 2024）？
  □ set_var/remove_var 是否在 unsafe 块中调用（Edition 2024）？

  【异步】
  □ 公开 trait 中的 async 方法是否用了 trait_variant 或显式 + Send？
  □ select! 循环中每个分支是否取消安全？
  □ 阻塞操作是否用了 spawn_blocking？
  □ 所有异步操作是否设置了超时？

  【并发】
  □ 跨线程共享可变数据是否用了 Mutex/RwLock？
  □ 锁持有时间是否最小化？
  □ 锁内是否有 await 或外部服务调用？

  【性能】
  □ 已知数量的集合是否用了 with_capacity？
  □ 是否避免了不必要的 clone()？
  □ 是否避免了不必要的 collect()？
  □ release profile 是否配置了 lto 和 codegen-units = 1？

  【命名】
  □ 类型/Trait/Enum 变体是否用了 UpperCamelCase？
  □ 函数/方法/变量是否用了 snake_case？
  □ 常量/静态变量是否用了 SCREAMING_SNAKE_CASE？
  □ Getter 是否避免了 get_ 前缀？
  □ 转换方法是否正确区分了 as_/to_/into_？
  □ 缩写词是否视为一个单词（Uuid 非 UUID）？

  【模块】
  □ 内部项是否用了 pub(crate) 而非裸 pub？
  □ 公共 API 是否通过 lib.rs 的 pub use 扁平化？
  □ 模块文件是否用了 foo.rs + foo/ 而非 mod.rs？
  □ lib.rs 顶部是否有 //! crate 级文档？

  【文档】
